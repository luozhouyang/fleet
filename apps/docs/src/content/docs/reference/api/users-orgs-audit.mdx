These endpoints manage accounts and organizations, expose the privileged-action
audit log, and create machine pairing codes. All paths start with `/api/v1`.

A user is a global account. Its role and resources come from one membership per
organization, so the same account can be an owner in one organization and a
viewer in another. The active organization is selected with `X-Fleet-Org` (see
[the REST API overview](/reference/api/#organization-scoping)) or defaults to a
team organization the caller belongs to.

## Authentication and authorization

Calls use `Authorization: Bearer flu_...`, the legacy `fla_...` bootstrap token,
or a browser session cookie from
[`POST /api/v1/auth/session`](/reference/api/#browser-sessions). Deployments can
also enable GitHub or Google sign-in; see
[OAuth sign-in](/reference/api/#oauth-sign-in).

Roles are `owner`, `admin`, `member`, and `viewer`:

| Capability | Owner | Admin | Member | Viewer |
| --- | --- | --- | --- | --- |
| Rename or delete the organization | yes | no | no | no |
| Invite, remove, or re-role members below owner | yes | yes | no | no |
| Manage machines | yes | yes | no | no |
| Use machines, sessions, and Git writes | yes | yes | yes | no |
| Read the audit log | yes | yes | no | no |

Members and viewers receive `403` on management endpoints. A viewer is otherwise
read-only, with one exception: any user may rotate its own token. Cross-organization
object lookups return `404` rather than confirming the resource exists.

The legacy bootstrap token is unscoped: it sees every organization and can
recover machines that lost their owner. It cannot create a browser session or
open the event socket.

## Current principal

`GET /api/v1/me` returns the caller's identity and active organization:

```json
{
  "kind": "user",
  "user": {
    "id": "user_...",
    "email": "ada@example.com",
    "name": "Ada",
    "created_at": "2026-01-02T03:04:05Z",
    "updated_at": "2026-01-02T03:04:05Z",
    "token_issued_at": "2026-01-02T03:04:05Z",
    "token_expires_at": "2026-02-01T03:04:05Z"
  },
  "org_id": "org_default",
  "role": "member"
}
```

The legacy admin token reports `kind: "legacy_admin"`, `user: null`, and
`org_id: null`.

## List users

`GET /api/v1/users` returns the members of the active organization (or the
organization named by `?org_id=`). The legacy admin sees every account.

A `User` contains `id`, `email`, `name`, `avatar_url`, `created_at`,
`updated_at`, `token_issued_at`, `token_expires_at`, and `disabled_at`. Roles
live on memberships, so use the members endpoint when you need the role.

`token_expires_at: null` means the token never expires. Disabled accounts are
included so they can be re-enabled.

## Create a user

`POST /api/v1/users` creates a global account, adds it to the target
organization, and returns its bearer token. The plaintext token is shown exactly
once.

Body:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `email` | string | Yes | Verified email; the account key for invitations and identity linking |
| `name` | string | Yes | Display name and audit actor; 1 to 120 characters |
| `org_id` | string | No | Target organization; defaults to the active one |
| `role` | string | Yes | `owner`, `admin`, `member`, or `viewer` |
| `token_expires_in_days` | integer | No | Lifetime in days; `0` means never. Omit to use `auth.user_token_ttl_days`. Values above `3650` are rejected. |

| Status | When |
| --- | --- |
| `200` | Response is `{"user":{...},"membership":{...},"token":"flu_..."}` |
| `400` | Invalid email or name, unknown role, or excessive expiry |
| `403` | The caller's role may not grant the requested role |
| `409` | An account for that email already exists |

The new account also gets a personal organization. The `user.create` audit entry
records the expiry, never the token.

```bash
curl -sS -X POST "$FLEET_URL/api/v1/users" \
  -H "Authorization: Bearer $FLEET_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"org_id":"org_default","email":"ada@example.com","name":"Ada","role":"member"}'
```

<Aside type="danger" title="The token is shown once">
  The response is the only time the plaintext token appears. Store it
  immediately. If it is lost, rotate the token.
</Aside>

## Change account state

`POST /api/v1/users/{id}/disable` blocks the bearer token and revokes every
browser session. Running agents are not stopped: the daemon owns those
processes. The account and its memberships stay, so it can be restored.

`POST /api/v1/users/{id}/enable` restores a disabled account. The previous
bearer token becomes valid again; rotate it first if it may have leaked while the
account was disabled. Revoked browser sessions stay revoked.

Both return the updated `User`. Administrators cannot change their own account
state (`400`). Members and viewers receive `403`; another organization's user
returns `404`. Disabling twice is idempotent.

## Delete a user

`DELETE /api/v1/users/{id}` permanently removes an account and returns `204`.
Identity links, browser sessions, memberships, and pending invitations go with
it. Machines, workspaces, agent sessions, and audit rows are untouched; audit
rows keep the actor name snapshot.

Administrators cannot delete themselves (`400`). An unknown or
cross-organization user returns `404`.

## Rotate a token

`POST /api/v1/users/{id}/rotate-token` returns
`{"user_id":"...","token":"flu_...","token_expires_at":"..."}`. The previous
token stops working immediately.

`expires_in_days` overrides the configured lifetime: `0` means never, values
above `3650` return `400`. Omitting it keeps the empty-body contract and applies
`auth.user_token_ttl_days`.

A user may rotate its own token without an admin role, including a viewer.
Rotating another user requires an admin in the same organization; anyone else
receives `403`, and an unknown or foreign user `404`. The `user.rotate_token`
audit entry records the expiry, never the token.

## Organizations

`GET /api/v1/orgs` returns every organization the caller belongs to, with its
role, oldest first:

```json
[
  {
    "organization": {
      "id": "org_default",
      "name": "Default",
      "kind": "team",
      "owner_user_id": "user_...",
      "created_at": "2026-01-01T00:00:00Z",
      "updated_at": "2026-01-01T00:00:00Z"
    },
    "role": "owner"
  }
]
```

`kind` is `personal` or `team`. Every account has one personal organization,
created lazily and hidden from the switcher while a team exists. Personal spaces
can be renamed but not deleted or left.

`POST /api/v1/orgs` creates a team organization and makes the caller its owner.
The bootstrap token creates an ownerless organization; the first owner
membership that is added adopts it.

`PATCH /api/v1/orgs/{org_id}` renames an organization and requires ownership.
`DELETE /api/v1/orgs/{org_id}` soft-deletes a team organization and returns
`202`. Its machines stay registered but lose their owner; the delete never
removes machines, workspaces, sessions, or audit history. The bootstrap admin
lists and claims unowned machines:

```http
GET /api/v1/admin/unowned-machines
POST /api/v1/admin/claim-machine   {"machine_id":"...","org_id":"..."}
```

## Members

`GET /api/v1/orgs/{org_id}/members` returns `OrgMember` records with `user_id`,
`email`, `name`, `avatar_url`, `role`, and timestamps. Emails are omitted unless
the caller administers the organization.

`POST /api/v1/orgs/{org_id}/members` adds an existing account by email:

```json
{ "email": "ada@example.com", "role": "member" }
```

`PATCH /api/v1/orgs/{org_id}/members/{user_id}` changes a role and
`DELETE` removes the member. Rules:

- An admin may grant roles below owner; only an owner may grant `owner`.
- The last owner can never be removed or demoted (`409`).
- Only an owner may remove an owner.
- `POST /api/v1/orgs/{org_id}/leave` leaves a team organization; the last owner
  must transfer ownership first (`409`).

## Invitations

Invite an email that has no account yet:

```json
{ "email": "new@example.com", "role": "member" }
```

The response is `{"invitation":{...},"token":"..."}`. The token is shown once and
no email is sent; share it out of band. When a user signs in through OAuth with
that verified email, the invitation is accepted and the membership is created.
Admins cannot invite an email that already has an account (`409`) or grant
`owner` unless they are an owner.

`GET /api/v1/orgs/{org_id}/invitations` lists pending invitations and `DELETE
/api/v1/orgs/{org_id}/invitations/{invitation_id}` revokes one.

## Audit

`GET /api/v1/audit` returns `{"entries":[...]}` newest first, filtered to the
caller's organization; the legacy admin sees every organization.

| Query | Type | Required | Description |
| --- | --- | --- | --- |
| `limit` | integer | No | Maximum entries; default `100`, clamped to `1` through `500` |

Each entry has `id`, `actor`, `action`, `subject`, `details`, and `created_at`.
`subject` is usually a workspace, user, or organization id. Git writes include
`outcome` (`ok`, `denied`, or `error`). Administration actions such as
`user.create`, `user.disable`, `org.member.role`, `auth.login`, and
`auth.session.create` are recorded without secrets.

Identity events are structured as well:

- `auth.login` carries the provider that authenticated the sign-in.
- `user.create` from an OAuth sign-in includes the provider, `source: "oauth"`,
  and whether the account came from the bootstrap administrator list.
- `auth.identity.link` is written when an OAuth identity is attached to an
  existing account because the verified email matched. It records the provider
  and `reason: "email_match"`.
- `org.member.add` includes the role and, for invitation acceptance at sign-in,
  `source: "invitation"` and the invitation id.

## Pairing codes

`POST /api/v1/pairing/codes` creates a single-use code a daemon redeems to pair.

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `org_id` | string | No | Target organization; a user admin is forced to its own |
| `machine_name` | string | No | Hint shown during pairing |

The response contains `id`, `code`, `expires_at`, and `org_id`. An unknown
organization returns `404`; members and viewers receive `403`. Pairing-code
creation writes the code and its audit row in one transaction.

<Aside type="note" title="Deleting an organization keeps its machines">
  Organization deletion removes memberships, pending invitations, and unused
  pairing codes, and sets machine ownership to unowned. It never deletes
  machines, workspaces, agent sessions, used pairing codes, or audit history.
  Only the bootstrap token can list and claim unowned machines.
</Aside>

## Backup

`GET /api/v1/admin/backup` returns a consistent `VACUUM INTO` snapshot as
`application/vnd.sqlite3` with a download filename. Only the bootstrap token
may call it; a user token receives `403`. The response is audited as
`admin.backup` without credentials. Restore is an offline operation: stop the
admin, replace its database, and start it again. `fleet admin restore`
automates the swap and keeps the previous database as a `.bak` file.
