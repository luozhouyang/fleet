These endpoints manage the people and organizations that use Fleet, expose the
privileged-action audit log, and create machine pairing codes. All paths start
with `/api/v1`.

## Authentication and authorization

Calls use `Authorization: Bearer <token>` with an `fla_` admin token or an
`flu_` user token. User and organization management, audit, and pairing
endpoints require the `admin` role. Members and viewers receive `403` with
`code: "forbidden"`, with one exception: a member may rotate its own token.

Two admin scopes exist:

- The legacy admin token is a super-admin. It sees every organization, can
  filter across them, and is the only credential that can create an
  organization.
- A user with the `admin` role is scoped to its own organization. It manages
  only users, audit entries, and pairing codes in that organization. Naming
  another organization during user creation or pairing-code selection returns
  `403`; looking up another organization's user by id returns `404`.

A member may rotate its own token. Rotating another user's token requires an
admin role in the same organization. Viewers are read-only, so the auth
middleware rejects their non-safe methods, including token rotation, with
`403`.

## Endpoints

| Method | Path | Purpose | Auth |
| --- | --- | --- | --- |
| GET | `/api/v1/users?org_id=` | List users | Admin |
| POST | `/api/v1/users` | Create a user and return its token once | Admin |
| DELETE | `/api/v1/users/{id}` | Delete a user | Admin |
| POST | `/api/v1/users/{id}/rotate-token` | Replace a user's bearer token | Member self or same-org admin |
| GET | `/api/v1/orgs` | List organizations | Admin |
| POST | `/api/v1/orgs` | Create an organization | Legacy admin only |
| GET | `/api/v1/audit?limit=` | List privileged-action audit entries | Admin |
| POST | `/api/v1/pairing/codes` | Create a single-use machine pairing code | Admin |

## List users

`GET /api/v1/users` returns `200` with an array of `User` objects.

Query:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `org_id` | string | No | Restrict results to one organization |

A user admin always sees its own organization; the `org_id` filter is ignored
for that caller. The legacy admin may filter by any organization. A non-admin
returns `403`.

A `User` contains `id`, `org_id`, `name`, `role`, `created_at`, and
`updated_at`. Roles are `admin`, `member`, and `viewer`.

```bash
curl -sS "$FLEET_URL/api/v1/users?org_id=org_default" \
  -H "Authorization: Bearer $FLEET_TOKEN"
```

## Create a user

`POST /api/v1/users` creates a user and returns `200` with the user and its
bearer token. The plaintext token is returned exactly once and is never stored.

Body:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `org_id` | string | Yes | Organization that owns the user |
| `name` | string | Yes | Display name and audit actor; 1 to 120 characters |
| `role` | string | Yes | `admin`, `member`, or `viewer` |

| Status | When |
| --- | --- |
| `200` | User created; response is `{"user":{...},"token":"flu_..."}` |
| `400` | Name is empty or longer than 120 characters, or `role` is not recognized |
| `403` | Target organization is outside the caller's scope |
| `404` | Organization does not exist |

```bash
curl -sS -X POST "$FLEET_URL/api/v1/users" \
  -H "Authorization: Bearer $FLEET_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"org_id":"org_default","name":"Ada","role":"member"}'
```

<Aside type="danger" title="The token is shown once">
  The response is the only time the plaintext token appears. Store it
  immediately. If it is lost, rotate the token to issue a new one.
</Aside>

## Delete a user

`DELETE /api/v1/users/{id}` permanently removes a user and returns `204` with no
body. The request is audited as `user.delete`.

An administrator cannot delete itself through this endpoint; that returns
`400`. An unknown user, or one in another organization, returns `404`.

## Rotate a token

`POST /api/v1/users/{id}/rotate-token` issues a new bearer token and returns
`200` with `{"user_id":"...","token":"flu_..."}`. The previous token stops
working immediately.

A member can rotate its own token without an admin role. A viewer cannot rotate
even its own token, because the auth middleware rejects non-safe methods with
`403`. Rotating another user's token requires an admin in the same
organization; a member attempting it receives `403`. An unknown or
cross-organization user returns `404`.

## List organizations

`GET /api/v1/orgs` returns `200` with an array of `Organization` objects. A user
admin sees only its own organization; the legacy admin sees all of them.

An `Organization` contains `id`, `name`, and `created_at`.

## Create an organization

`POST /api/v1/orgs` creates an organization and returns `200` with the new
`Organization`. Only the legacy admin token can call it, because a user admin is
already scoped to one organization.

Body:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `name` | string | Yes | Display name; 1 to 120 characters |

| Status | When |
| --- | --- |
| `200` | Organization created |
| `400` | Name is empty or longer than 120 characters |
| `403` | Caller is a user admin, member, or viewer |

## List audit entries

`GET /api/v1/audit` returns `200` with an audit page and is admin-only. Entries
are newest first and filtered to the caller's organization; the legacy admin
sees every organization.

Query:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `limit` | integer | No | Maximum entries; default `100`, clamped to `1` through `500` |

Response:

| Field | Type | Description |
| --- | --- | --- |
| `entries` | array | Audit entries, newest first |

Each entry contains `id`, `actor`, `action`, `subject`, `details`, and
`created_at`. `subject` is usually a workspace or user id. `details` is
structured context; Git writes include `outcome` (`ok`, `denied`, or `error`)
and their request fields.

The admin applies the organization filter before the limit, so newer entries
from another organization cannot crowd out the caller's history.

## Create a pairing code

`POST /api/v1/pairing/codes` creates a single-use code that a daemon redeems to
pair with the admin. It returns `200` with the code and its expiry.

Body:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `org_id` | string | No | Target organization |
| `machine_name` | string | No | Hint shown during pairing |

A user admin is forced to its own organization; naming a different `org_id`
returns `403`. The legacy admin may name any organization and defaults to
`org_default`. An unknown organization returns `404`. Members and viewers
receive `403`.

Response:

| Field | Type | Description |
| --- | --- | --- |
| `id` | string | Pairing-code record id |
| `code` | string | Plaintext pairing code, shown once |
| `expires_at` | timestamp | Expiry time |
| `org_id` | string | Organization the paired machine joins |

```bash
curl -sS -X POST "$FLEET_URL/api/v1/pairing/codes" \
  -H "Authorization: Bearer $FLEET_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"machine_name":"workstation"}'
```

<Aside type="note" title="Audit records cover administration and Git writes">
  User creation, deletion, and token rotation, organization creation, pairing
  code creation, and every Git write attempt are audited. Most audit writes are
  best effort and do not fail the request, but pairing-code creation records the
  code and its audit row in one transaction.
</Aside>

<Aside type="caution" title="User admins cannot create organizations">
  A user with the `admin` role can manage its own organization's users and
  pairing codes, but `POST /api/v1/orgs` is reserved for the legacy admin token.
  Use the legacy token when bootstrapping a new organization.
</Aside>
