Sessions represent running agent processes on a machine. These endpoints create,
inspect, control, and delete sessions, and resolve the permission and user
question requests an agent raises. All paths start with `/api/v1`.

## Authentication and authorization

Calls use `Authorization: Bearer <token>` with an `fla_` admin token or an
`flu_` user token. A session inherits its organization from its machine, and a
permission inherits it from its session. Cross-organization lookups return
`404`.

Every role in the organization can read sessions and permissions. Creating,
closing, deleting, messaging, interrupting, resuming, and approving require a
member or admin; the auth middleware rejects a viewer's non-safe method with
`403`.

Every session-scoped endpoint returns `404` for an unknown session or one owned
by another organization. Permission and question requests are resolved through
their session, so an unknown or out-of-scope request also returns `404`.

Operations that reach the daemon need a live machine socket. An offline machine
returns `503` with `code: "machine_offline"`. Permission and question payloads
are live-only: the admin does not store them. When the machine is offline the
`permissions` and `questions` arrays are empty rather than served from a cache.

## Endpoints

| Method | Path | Purpose | Auth |
| --- | --- | --- | --- |
| GET | `/api/v1/sessions?include_closed=` | List persisted and live sessions | Any role with machine access |
| POST | `/api/v1/sessions` | Create a session on a machine | Member or admin |
| GET | `/api/v1/sessions/{id}` | Fetch session detail | Any role with session access |
| DELETE | `/api/v1/sessions/{id}` | Delete a session and its history | Member or admin |
| POST | `/api/v1/sessions/{id}/close` | Shut down and archive a session | Member or admin |
| POST | `/api/v1/sessions/{id}/messages` | Send a user message | Member or admin |
| POST | `/api/v1/sessions/{id}/interrupt` | Interrupt the current turn | Member or admin |
| POST | `/api/v1/sessions/{id}/resume` | Resume an interrupted session | Member or admin |
| GET | `/api/v1/sessions/{id}/permissions` | List live permission requests | Any role with session access |
| POST | `/api/v1/sessions/{id}/permissions/{permission_id}/approve` | Approve a permission request | Member or admin |
| POST | `/api/v1/sessions/{id}/permissions/{permission_id}/reject` | Reject a permission request | Member or admin |
| GET | `/api/v1/sessions/{id}/questions` | List live user question requests | Any role with session access |
| POST | `/api/v1/sessions/{id}/questions/{question_id}/answer` | Answer a user question | Member or admin |
| POST | `/api/v1/sessions/{id}/questions/{question_id}/reject` | Reject a user question | Member or admin |

Session creation, messages, interrupt, close, permission decisions and question
answers accept an [`Idempotency-Key`](/reference/api/#idempotent-retries) so a
retried request executes once. Resume does not: a resume is safe to repeat and
does not take a key.

## List sessions

`GET /api/v1/sessions` merges persisted session rows with the live session
lists reported by connected daemons and returns `200` with an array of
`AgentSession` objects. Daemon failures are best effort and never fail the
request; persisted rows are kept.

Query:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `include_closed` | boolean | No | Include `terminated` sessions; default `false` |

By default the list hides terminated sessions and includes active, interrupted,
completed, and failed ones. Results are sorted by `updated_at`, newest first.

The merge reconciles stale state:

- An active session on an offline machine becomes `interrupted` with
  `metadata.machine_offline: true` and a `machine_offline` error.
- A session the daemon no longer reports becomes `interrupted` with
  `metadata.orphaned: true` and a `session_not_reported` error.

An `AgentSession` contains:

| Field | Type | Description |
| --- | --- | --- |
| `id` | string | Stable session id |
| `machine_id` | string | Owning machine |
| `workspace_id` | string, optional | Associated workspace |
| `provider` | string | Provider adapter id, such as `claude`, `codex`, or `mock` |
| `agent_type` | string | Concrete agent type, such as `claude-code` |
| `status` | string | Lifecycle status |
| `cwd` | string | Working directory |
| `title` | string, optional | Display title |
| `created_at`, `updated_at` | timestamp | Lifecycle timestamps |
| `last_error` | object, optional | Latest error as `{"code":"...","message":"..."}` |
| `metadata` | object | Provider-specific and reconciliation metadata |

Statuses are `creating`, `starting`, `running`, `waiting_for_input`,
`waiting_for_permission`, `waiting_for_question`, `interrupted`, `completed`,
`failed`, and `terminated`.

## Create a session

`POST /api/v1/sessions` asks the machine's daemon to start an agent and returns
`200` with the new `AgentSession`.

Body:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `machine_id` | string | Yes | Connected machine that runs the agent |
| `workspace_id` | string | No | Workspace on that machine |
| `provider` | string | No | Provider adapter id |
| `cwd` | string | No | Working directory; defaults to the workspace root |
| `title` | string | No | Display title |
| `model` | string | No | Provider model id |

The daemon also accepts optional `system_prompt`, `allowed_tools`, `env`, and
`extra` fields. They are forwarded unchanged.

When `workspace_id` is supplied, it must belong to `machine_id`, otherwise the
request returns `400`. If `cwd` is omitted, the workspace root is used.

| Status | When |
| --- | --- |
| `200` | Session created |
| `400` | `machine_id` is empty, or the workspace belongs to another machine |
| `404` | Caller cannot access the machine or workspace |
| `503` | Machine is offline |

```bash
curl -sS -X POST "$FLEET_URL/api/v1/sessions" \
  -H "Authorization: Bearer $FLEET_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"machine_id":"m_abc","workspace_id":"ws_abc","provider":"claude","title":"Fix tests"}'
```

## Get session detail

`GET /api/v1/sessions/{id}` returns `200` with a `SessionDetail`:

| Field | Type | Description |
| --- | --- | --- |
| `session` | object | The `AgentSession` |
| `turns` | array | `AgentTurn` values |
| `messages` | array | `AgentMessage` values |
| `tool_calls` | array | `AgentToolCall` values |
| `permissions` | array | Live `AgentPermissionRequest` values |
| `questions` | array | Live `AgentQuestionRequest` values |
| `plan` | object, optional | The latest `AgentPlan`, omitted when the agent never published one |

When the machine is online, the detail is proxied from the daemon. When the
machine is offline, or the daemon no longer knows the session, the endpoint
returns stored metadata with `metadata.history_unavailable: true` and empty
`turns`, `messages`, `tool_calls`, `permissions`, `questions`, and no `plan`.
Permission and question payloads are never persisted by the admin; only the
daemon persists the latest plan.

An unknown session, or one owned by another organization, returns `404`.

<Aside type="note" title="The daemon owns the transcript">
  The admin stores session metadata only, not the conversation transcript or
  live permission and question payloads. An offline session is readable but its
  history is deliberately empty rather than partially reconstructed from cache.
</Aside>

## Delete a session

`DELETE /api/v1/sessions/{id}` forwards `agent.sessions.delete` to the daemon,
removes the admin's local session row, and returns `200` with the daemon's JSON
response. Unlike close, deletion permanently removes history.

An offline machine returns `503`. An unknown or out-of-scope session returns
`404`.

## Close a session

`POST /api/v1/sessions/{id}/close` forwards `agent.sessions.shutdown`, marks the
session `terminated`, and returns `200` with the daemon's JSON response. Metadata
and history remain available in later listings when `include_closed=true`.

An offline machine returns `503`.

## Send a message

`POST /api/v1/sessions/{id}/messages` forwards `agent.sessions.send_message` and
returns `200` with the daemon's acknowledgment.

Body:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `content` | string | Yes | User message text |
| `attachments` | array | No | Attachments with `name`, optional `mime_type`, and base64 `data_base64` |

The daemon delivers attachments to the agent as structured image parts. The
recorded user message keeps only the typed text plus `[attachment: name (mime)]`
lines, so base64 payloads never enter the transcript, event stream or message
store.

An offline machine returns `503`.

## Interrupt a session

`POST /api/v1/sessions/{id}/interrupt` forwards `agent.sessions.interrupt` and
returns `200` with the daemon's JSON response. An offline machine returns `503`.

## Resume a session

`POST /api/v1/sessions/{id}/resume` forwards `agent.sessions.resume` and returns
`200` with the daemon's JSON response. An offline machine returns `503`.

## List permissions

`GET /api/v1/sessions/{id}/permissions` returns `200` with an array of live
`AgentPermissionRequest` values proxied from the daemon. The admin does not
store permission payloads: when the machine is offline, or the daemon no
longer knows the session, the endpoint returns an empty array.

Each request contains `id`, `session_id`, optional `turn_id` and `tool_call_id`,
`tool_name`, `description`, `input`, `options`, `status`, `created_at`, and
optional `resolved_at` and `expires_at`. Statuses are `pending`, `approved`,
`rejected`, `timed_out`, `cancelled`, and `delivery_failed`.

## Approve a permission

`POST /api/v1/sessions/{id}/permissions/{permission_id}/approve` forwards
`agent.permissions.respond` with `approve: true`.

Body is optional:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `option_id` | string | No | Provider-native option to select, such as `allow_once` |
| `message` | string | No | Note sent back to the provider |

When `option_id` is omitted the daemon selects the first `allow_*` option
reported by the provider. The response is `{"ok":true}` after the daemon
resolves the request.

| Status | When |
| --- | --- |
| `200` | Decision delivered to the daemon |
| `403` | Caller is a viewer |
| `404` | Session or permission is unknown or out of scope |
| `409` | Permission is already resolved; the daemon rejects the second decision |
| `503` | Machine is offline |

```bash
curl -sS -X POST "$FLEET_URL/api/v1/sessions/sess_abc/permissions/perm_abc/approve" \
  -H "Authorization: Bearer $FLEET_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"option_id":"allow_once","message":"Approved for this run"}'
```

## Reject a permission

`POST /api/v1/sessions/{id}/permissions/{permission_id}/reject` has the same
body, authorization, and status codes as approval, but forwards `approve: false`.
When `option_id` is omitted the daemon selects the first `reject_*` option.

## List questions

`GET /api/v1/sessions/{id}/questions` returns `200` with an array of live
`AgentQuestionRequest` values proxied from the daemon. Like permissions, user
questions are live-only: an offline machine returns an empty array.

Each request contains `id`, `session_id`, optional `turn_id` and
`tool_call_id`, `questions`, `status`, `created_at`, and optional
`resolved_at` and `expires_at`. Each question contains `id`, optional `header`,
`question`, `options`, `multi_select`, `allow_custom`, and `is_secret`.
Question statuses are `pending`, `answered`, `rejected`, `timed_out`,
`cancelled`, and `delivery_failed`.

## Answer a question

`POST /api/v1/sessions/{id}/questions/{question_id}/answer` forwards
`agent.questions.respond` with `reject: false`.

Body is optional:

| Field | Type | Required | Description |
| --- | --- | --- | --- |
| `answers` | array | Answering only | One `AgentQuestionAnswer` per question, with `id`, `selected`, and optional `custom`. Omit when rejecting. |
| `message` | string | No | Informational note carried in the decision; providers without a message channel ignore it |

The response is `{"ok":true}` after the daemon resolves the request. The daemon
validates answers strictly: every question must have exactly one answer with a
unique `id`, single-select questions accept at most one `selected` label, each
label must exist in the question's `options`, `custom` requires
`allow_custom`, and `custom` is capped at 8 KiB. A violation returns `400`.

| Status | When |
| --- | --- |
| `200` | Answer delivered to the daemon |
| `400` | Answers fail validation, for example a missing answer, a duplicate id, or an unoffered label |
| `403` | Caller is a viewer |
| `404` | Session or question is unknown or out of scope |
| `409` | Question is already resolved; the daemon rejects the second decision |
| `503` | Machine is offline |

## Reject a question

`POST /api/v1/sessions/{id}/questions/{question_id}/reject` has the same body,
authorization, and status codes as answering, but forwards `reject: true` so
the provider receives a declined elicitation.

<Aside type="caution" title="The daemon owns the decision">
  Permission and question requests are resolved atomically on the daemon. The
  admin only caches the session-to-machine mapping and proxies the decision, so
  the second decision for the same request returns `409`.
</Aside>

<Aside type="caution" title="503 means the command was not delivered">
  Message, interrupt, resume, close, delete, permission, and question decisions
  are not queued while a machine is offline. Retry after the daemon reconnects.
  Reads of session metadata and the transcript still succeed, but permission
  and question arrays are empty.
</Aside>
