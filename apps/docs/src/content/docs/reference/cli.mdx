The `fleet` binary is the control surface for installation, process management, and both service roles. It ships with two server binaries it can launch, inspect, and supervise: `fleet-admin` and `fleet-daemon`.

Build the CLI with:

<Tabs>
  <TabItem label="Cargo">
    ```sh
    cargo build -p fleet-cli
    ```
  </TabItem>
  <TabItem label="pnpm">
    ```sh
    pnpm build:cli
    ```
  </TabItem>
</Tabs>

Build the server binaries with `cargo build -p fleet-admin -p fleet-daemon`.

## Global flags

These flags are accepted by every `fleet` subcommand.

| Flag | Environment | Default | Purpose |
| --- | --- | --- | --- |
| `--admin-url <url>` | `FLEET_ADMIN_URL` | `http://127.0.0.1:8787` | Admin base URL used by client commands. |
| `--admin-token <token>` | `FLEET_ADMIN_TOKEN` | `cli.toml` token | Bearer token for the admin API. |
| `--cli-config <path>` | `FLEET_CLI_CONFIG` | `~/.fleet/cli.toml` | CLI configuration file. |
| `--json` | - | `false` | Print raw JSON instead of tables. `output = "json"` in `cli.toml` has the same effect. |

## Shared role flags

`fleet admin ...` and `fleet daemon ...` both accept these global role flags anywhere within the role namespace.

| Flag | Purpose |
| --- | --- |
| `--config <path>` | Role TOML. Default `~/.fleet/<role>/config.toml`. |
| `--state-dir <path>` | Role state directory. Default `~/.fleet/<role>`. |
| `--bin <path>` | Server binary. Defaults to `FLEET_ADMIN_BIN` or `FLEET_DAEMON_BIN`, then a sibling of `fleet`, then `PATH`. |

There is no `--user` / `--system` scope selector. Fleet has one server profile:
configuration and state always live under `~/.fleet`, and the system service
runs as the invoking user. Service definitions live in the platform service
manager; `start`, `stop`, `restart`, and `install-service` ask for sudo once
when they need to write or control a system unit.

## Top-level commands

```text
fleet [global flags] <command>

install --from-dir DIR [--prefix DIR] [--port PORT] [--yes] [--force] [--dry-run]
install --repair [--prefix DIR] [--yes]
status
doctor
upgrade [--version latest|vX.Y.Z] [--force] [--no-restart] [--yes] [--dry-run]
uninstall [--keep-data | --delete-data] [--yes] [--dry-run]
```

`install` is the single installer entry point. It rejects root, writes only
user-owned files without elevation, then installs both role services and the
watchdog with fixed privileged commands. `--repair` re-renders the service
definitions from `~/.fleet` without replacing binaries. `upgrade` replaces the
binaries and web assets next to the running `fleet` from a published release
and rolls back when the restarted services do not become ready. `uninstall`
removes installed services, the watchdog, and binaries; `--delete-data` (alias
`--purge`) also removes configuration and data, while `--keep-data` is the
explicit default.

## Admin commands

```text
fleet admin [role flags] <command>

setup
  --bind <host:port>            --database <path>
  --web-dir <path>              --no-web
  --rotate-admin-token          --no-cli-config
  --install-service             --no-install-service
  --start                       --yes
  --dry-run

config show [--reveal]
config path
config validate

start    [--mode auto|service|supervisor] [--timeout 15]
stop     [--mode auto|service|supervisor] [--timeout 15]
restart  [--mode auto|service|supervisor] [--timeout 15]
status   [--mode auto|service|supervisor] [--timeout 15]
logs     [-f|--follow] [-n|--lines 200] [--mode ...] [--supervisor]
run
install-service   [--yes] [--dry-run]
uninstall-service [--yes] [--dry-run]
health

machines list
machines get <id>
machines delete <id> [--yes]
machines revoked
machines unrevoke <id>
machines reconnect <id>
machines rotate-token <id> [--cancel]
machines providers <id>
machines move-org <id> <org-id>
machines pair-code [--org <id>] [--name <name>]

workspaces list [--machine <id>]
workspaces get <id>
workspaces add --machine <id> --root <path> [--name <name>]
workspaces remove <id> [--yes]

sessions list
sessions get <id>
sessions create --machine <id> --workspace <id> [--provider <id>] [--title <text>] [--model <name>]
sessions send <id> <message>
sessions permissions <id>
sessions interrupt <id>
sessions resume <id>
sessions close <id> [--yes]
sessions delete <id> [--yes]

users list [--org <id>]
users create --org <id> --email <email> --name <name> --role owner|admin|member|viewer
users delete <id> [--yes]
users rotate-token <id> [--yes]
users disable <id> [--yes]
users enable <id> [--yes]

orgs list
orgs create --name <name>
orgs members --org <id>
orgs invite --org <id> --email <email> --role owner|admin|member|viewer

backup [--out <path>] [--force]
restore --from <path> [--yes]

audit [--limit 100] [--out <path>]
permissions approve <session_id> <permission_id>
permissions reject <session_id> <permission_id>
```

`permissions approve` and `permissions reject` act on a permission inside a session; both arguments are required because permissions are session-scoped. `machines delete` revokes a machine instead of erasing its audit history; recover it with `machines unrevoke`. `machines rotate-token` requires an online daemon; the daemon must persist the new token before the admin records the rotation, and `--cancel` abandons a rotation that was never confirmed. `users create` and `users rotate-token` print a bearer token exactly once. `admin config validate` parses the admin TOML and also checks the recorded daemon config for conflicting paths.

`backup` asks the running admin for a consistent SQLite snapshot and writes it with owner-only permissions; `restore` refuses while the admin holds its database lock, keeps the previous database as a `.bak` file, and drops stale WAL files before installing the backup. `audit --out` writes the entries to a JSON file instead of printing them.

## Daemon commands

```text
fleet daemon [role flags] <command>

setup
  --org <id>                    --server <ws://host:port/ws/machine>
  --code <pairing-code>         --name <machine-name>
  --key-file <path>             --database <path>
  --workspace <path> (repeat)
  --store-token                 --configure-only
  --allow-insecure
  --install-service             --no-install-service
  --start                       --yes
  --dry-run

config show
config path
config validate

start    [--mode auto|service|supervisor] [--timeout 15]
stop     [--mode auto|service|supervisor] [--timeout 15]
restart  [--mode auto|service|supervisor] [--timeout 15]
status   [--mode auto|service|supervisor] [--timeout 15]
logs     [-f|--follow] [-n|--lines 200] [--mode ...] [--supervisor]
run
install-service   [--yes] [--dry-run]
uninstall-service [--yes] [--dry-run]

pair --server <ws-url> --code <code> [--name <name>]
providers
workspace add <root> [--name <name>]
workspace list
workspace remove <id> [--yes]
rotate-key
identity show
```

`daemon config validate` parses the daemon TOML and checks it against the recorded admin config. `daemon pair` saves a machine token without rewriting configuration; `daemon setup` writes configuration and then pairs. `daemon providers`, `daemon workspace`, and `daemon rotate-key` run the corresponding local operation through `fleet-daemon`.

## Network, setup, and diagnostics

```text
fleet network detect
fleet network wizard
  [--mode tailscale|cloudflare] [--hostname <name>]
  [--admin-config <path>] [--daemon-config <path>]
  [--cloudflared-config <path>] [--yes]

fleet network connect
  --provider tailscale|cloudflare
  [--hostname <name>] [--execute] [--yes]
  [--admin-config <path>] [--daemon-config <path>]
  [--cloudflared-config <path>]
  [--cloudflare-api-token <token>] [--cloudflare-account-id <id>]
  [--access-email <email>] [--access-domain <domain>] [--access-everyone]
  [--skip-access] [--skip-service] [--install]

fleet setup [--role admin|daemon|cli] [--yes] [-- <role arguments>]
fleet status
fleet doctor

fleet config init [--admin-url <url>] [--admin-token <token>]
                  [--output table|json] [--force]
fleet config show [--reveal]
fleet config validate
fleet config path
```

`fleet setup` is an interactive dispatcher: it prompts for a role when `--role` is omitted and forwards trailing arguments to the role-specific setup command. `fleet status` summarizes both roles. `fleet doctor` runs read-only diagnostics across binaries, configuration, permissions, database separation, and health.

`fleet network connect` only previews its plan unless `--execute` is passed. The Cloudflare API token can also come from `CLOUDFLARE_API_TOKEN`.

<Aside type="note" title="Hidden command">
`fleet __supervise` is an internal fallback supervisor entry point. It is hidden from help and is not part of the supported command surface.
</Aside>

## Direct server entry points

The server binaries also run standalone. They accept `--config <path>` and read the same environment variables as the CLI.

```text
fleet-admin [--config <path>] [serve]
  [--bind <host:port>] [--db <path>]
  [--admin-token <token>] [--web-dir <path>]

fleet-daemon [--config <path>] [serve]
fleet-daemon register-workspace <root> [--name <name>]
fleet-daemon providers
fleet-daemon list-workspaces
fleet-daemon remove-workspace <id> [--yes]
fleet-daemon rotate-key
fleet-daemon pair --server <ws-url> --code <code> [--name <name>]
```

With no subcommand, both binaries run their server. The `fleet` role namespaces are the recommended interface because they resolve paths and platform services for you.

`--mode service` selects the native service backend: systemd on Linux, launchd
on macOS, or Task Scheduler on Windows. Both Windows roles use startup tasks
with a stored credential so they run as the invoking user. `--mode supervisor`
forces the fallback supervisor. `install-service` and `uninstall-service` write
and remove the platform artifact with fixed privileged commands; on Unix they
ask for sudo once, and on Windows they require elevation (UAC).

## Exit codes

`fleet status`, `fleet admin status`, and `fleet daemon status` use the same contract:

| Code | Meaning |
| --- | --- |
| `0` | Healthy: the role is running and its health endpoint responds. |
| `1` | Stopped: no managed process or reachable service is running. |
| `2` | Degraded: running but unhealthy, conflicting with another supervisor, or unverified. |

Top-level `fleet status` combines both roles: it returns `2` if either role is degraded, otherwise `1` if either is stopped, otherwise `0`.

`fleet doctor` returns `0` when every check passes and `1` when any check reports `FAIL`; warnings alone do not change the exit code.

All other commands exit `0` on success and nonzero on error. Authentication, validation, and confirmation failures also exit nonzero.
