Fleet is a Cargo workspace and a pnpm workspace in one repository. The Rust
crates carry the control plane, the machine daemon, and the shared contracts;
the TypeScript workspace builds the browser UI. This page covers the day-to-day
loop for working on both.

Start with the [installation guide](/getting-started/installation/) if you only
want to build and run Fleet.

## Toolchain

| Tool | Version | Notes |
| --- | --- | --- |
| Rust | 1.88+ | `rust-version` in the workspace manifest |
| Node.js | 22 | Required by the Vite and Playwright toolchain |
| pnpm | 10.22 | Declared by `packageManager` in the root `package.json` |

The root `package.json` scripts set `PCARGO` to a prebuilt Cargo binary used by
the project maintainers. If that path does not exist on your machine, override
it with your own Cargo:

```bash
PCARGO=cargo pnpm build:rust
PCARGO=cargo pnpm test
```

Every script below accepts the same override. Without it, the script uses the
configured prebuilt binary.

## Repository layout

| Path | Contents |
| --- | --- |
| `apps/fleet-admin` | Control plane server: REST API, machine gateway, browser event stream, SPA hosting |
| `apps/fleet-daemon` | Machine daemon: connection client, session delivery, local services |
| `apps/fleet-cli` | `fleet` management CLI, setup flows, systemd delegation, fallback supervisor |
| `apps/web` | React 19, TanStack Router/Query, Tailwind, and Monaco UI |
| `apps/docs` | This documentation site |
| `crates/*` | Shared Rust libraries; see [Crate architecture](/project/crates/) |
| `packages/*` | Shared TypeScript packages: `api-client`, `protocol-types`, and `ui` |
| `packaging/systemd` | Unit templates rendered by the CLI and installer |

The dependency direction flows from `core-common` through `core-protocol` to
domain crates, then to the two server applications. The CLI does not link the
server crates; it runs and supervises their binaries. Keep new code on the
correct side of that boundary rather than importing across it.

## Local development

Development runs as one web-serving process: `pnpm dev` builds the UI and starts
`fleet-admin`, which serves both `/api` and the SPA on port 8787.

<Steps>
  <Step title="Install workspace dependencies">
    Run `pnpm web:install` once. This installs the pnpm workspace, including the
    web app and shared TypeScript packages.
  </Step>
  <Step title="Start the admin and UI">
    Run `pnpm dev`. It builds `apps/web/dist` and starts `fleet-admin` at
    `http://127.0.0.1:8787`. The script passes the development token
    `dev-token` unless `FLEET_ADMIN_TOKEN` is set.
  </Step>
  <Step title="Pair the machine">
    In a second terminal, run `fleet daemon setup` through pnpm. It creates a
    single-use pairing code, completes the challenge-response handshake, writes
    `~/.fleet/daemon/config.toml`, and stores the per-machine token in
    `~/.fleet/daemon/machine.key.token` with mode `0600`.
  </Step>
  <Step title="Start the daemon">
    Run `pnpm dev:daemon`. The daemon serves its loopback health endpoint on
    port 18080 and connects out to the admin.
  </Step>
  <Step title="Open the UI">
    Go to `http://127.0.0.1:8787`, choose the machine, register a workspace, and
    create a session. The `mock` provider needs no credentials.
  </Step>
</Steps>

```bash
pnpm web:install

pnpm dev

pnpm run fleet -- --admin-url http://127.0.0.1:8787 --admin-token dev-token daemon setup \
  --org org_default \
  --server ws://127.0.0.1:8787/ws/machine \
  --config ~/.fleet/daemon/config.toml \
  --name dev-machine

pnpm dev:daemon
```

`fleet daemon setup` must run while the admin is reachable. Re-running it with
the same key is safe; it issues a fresh code and rotates the per-machine token.
There is no shared machine token to configure.

For frontend hot reload, run `pnpm dev:web` instead of using the SPA served by
the admin. Vite listens on `http://127.0.0.1:5173` and proxies `/api` and `/ws`
to port 8787. Both `pnpm dev` and `pnpm dev:web` inject
`VITE_DEFAULT_API_TOKEN` from `FLEET_ADMIN_TOKEN` for local authentication only;
production builds embed no default token.

<Aside type="caution" title="Start from a clean state">
  This iteration has no backward compatibility. Development state lives under
  `~/.fleet`, and pre-rebrand configs and databases are not migrated. Delete
  the directory to reset, then pair the machine again.
</Aside>

## Builds

| Command | Result |
| --- | --- |
| `pnpm build:rust` | Debug build of every workspace crate |
| `pnpm build:release` | Release build with thin LTO and stripped debug info |
| `pnpm build:web` | Type-check and bundle the web UI into `apps/web/dist` |
| `pnpm build:cli` | Build the `fleet` binary at `target/debug/fleet` |

The admin auto-detects `apps/web/dist` when it sits next to the binary. For a
manual production run, pass `--web-dir` explicitly and keep `--db` on a stable
SQLite path. The CLI can also build and run through pnpm directly:
`pnpm run fleet -- --help`.

Release archives are produced by `.github/workflows/release.yml` when a `v*` tag
is pushed. The workflow builds Linux x86_64/arm64 as static musl binaries, macOS
arm64/x86_64 with the web UI, and a Windows x86_64 zip for foreground use. It
publishes `fleet-<os>-<arch>.tar.gz`, `fleet-windows-x86_64.zip`, and
`SHA256SUMS`. The public installer is `apps/docs/public/install.sh`, served at
`https://luozhouyang.github.io/fleet/install.sh`.

Linux release binaries link musl statically, so they do not depend on the host
glibc version. Build them locally with:

```bash
rustup target add x86_64-unknown-linux-musl
sudo apt-get install musl-tools
CC_x86_64_unknown_linux_musl=musl-gcc \
CARGO_TARGET_X86_64_UNKNOWN_LINUX_MUSL_LINKER=musl-gcc \
  cargo build --release --target x86_64-unknown-linux-musl \
  -p fleet-admin -p fleet-daemon -p fleet-cli
```

Use `aarch64-unknown-linux-musl` and `musl-gcc` on an arm64 host for the arm64
archive.

### macOS signing and notarization

The macOS jobs call `scripts/release/sign-macos.sh`. The job imports the
certificate into a temporary keychain, signs each binary with the hardened
runtime and a secure timestamp, verifies the signature, and submits a temporary
zip to `notarytool`. Both the certificate and the App Store Connect API key are
required by the `check-signing` job.

Add these repository secrets in **Settings → Secrets and variables → Actions**:

| Secret | Required | Meaning |
| --- | --- | --- |
| `APPLE_CERTIFICATE_P12` | for signing | Base64 of a **Developer ID Application** `.p12` |
| `APPLE_CERTIFICATE_PASSWORD` | with the certificate | Password used when exporting the `.p12` |
| `APPLE_TEAM_ID` | for notarization | Ten-character Apple Developer team id |
| `APPLE_API_KEY_P8` | for notarization | Base64 of the App Store Connect `AuthKey_<KEY_ID>.p8` |
| `APPLE_API_KEY_ID` | for notarization | App Store Connect API key id |
| `APPLE_API_ISSUER` | for notarization | App Store Connect issuer id (UUID) |
| `APPLE_SIGNING_IDENTITY` | optional | Full identity name; auto-detected when omitted |

The helper script exports the certificate, validates it, and writes every secret
without printing their values:

```bash
scripts/release/configure-signing.sh --issuer <app-store-connect-issuer-id>
```

The key id and issuer id are shown in App Store Connect under **Users and
Access → Integrations → App Store Connect API**. To configure manually:

1. In the Apple Developer portal, create a **Developer ID Application**
   certificate, download it, and import it into Keychain Access.
2. Export the certificate and private key as a password-protected `.p12`.
3. Base64-encode it and store the result as `APPLE_CERTIFICATE_P12`:

   ```bash
   base64 -i DeveloperID.p12 | pbcopy
   ```

4. Create an App Store Connect API key with the **Developer** role, download
   `AuthKey_<KEY_ID>.p8`, and base64-encode it into `APPLE_API_KEY_P8`. The key
   can only be downloaded once.
5. Copy the key id and the issuer UUID into `APPLE_API_KEY_ID` and
   `APPLE_API_ISSUER`.
6. Optionally set `APPLE_SIGNING_IDENTITY` to the exact identity, for example
   `Developer ID Application: Your Name (TEAMID1234)`. Otherwise the script
   selects the first Developer ID Application identity in the keychain.

Notarization requires a network connection and can take several minutes; the
workflow waits for the result and prints the notarization log on failure. Bare
command-line binaries cannot be stapled, so Gatekeeper verifies the notarization
ticket online. Ship a signed `.pkg` or `.dmg` instead if you need an
offline-stapled artifact.

Verify a downloaded binary locally with:

```bash
codesign --verify --strict --verbose=2 ./fleet-admin
spctl --assess --type execute --verbose=2 ./fleet-admin
```

If signing is configured but any step fails, the release job fails rather than
publishing an unsigned macOS archive.

### Windows signing

The Windows job calls `scripts/release/sign-windows.ps1` after building. When
`WINDOWS_CERTIFICATE_PFX` is set, the script writes the certificate to a
temporary file, signs each `.exe` with SHA-256 Authenticode and an RFC 3161
timestamp, and verifies the result with `signtool verify /pa /all`. Without the
secret it prints a notice and the zip contains unsigned binaries.

Add these repository secrets:

| Secret | Required | Meaning |
| --- | --- | --- |
| `WINDOWS_CERTIFICATE_PFX` | for signing | Base64 of a code-signing `.pfx` including the private key |
| `WINDOWS_CERTIFICATE_PASSWORD` | with the certificate | Password used when exporting the `.pfx` |
| `WINDOWS_TIMESTAMP_URL` | optional | RFC 3161 timestamp server; defaults to `http://timestamp.digicert.com` |

The certificate must be an Authenticode code-signing certificate (OV or EV) from
a public CA. Export it with the private key as `.pfx`, then write the secrets
from a machine that has `gh` authenticated:

```bash
# macOS
base64 -i codesign.pfx | tr -d '\n' > codesign.pfx.b64
# Linux
base64 -w0 codesign.pfx > codesign.pfx.b64

gh secret set WINDOWS_CERTIFICATE_PFX --repo luozhouyang/fleet < codesign.pfx.b64

read -rsp 'PFX password: ' WINDOWS_CERTIFICATE_PASSWORD; echo
printf '%s' "$WINDOWS_CERTIFICATE_PASSWORD" | \
  gh secret set WINDOWS_CERTIFICATE_PASSWORD --repo luozhouyang/fleet
unset WINDOWS_CERTIFICATE_PASSWORD
```

Windows binaries are built with the MSVC toolchain and require the Microsoft
Visual C++ Redistributable on the target machine. If signing is configured but
signing or verification fails, the job fails instead of publishing unsigned
executables.

## Service management

`fleet admin|daemon install-service` selects one backend:

| Platform | Backend | Installed artifact |
| --- | --- | --- |
| Linux with systemd | `systemd` | `/etc/systemd/system/fleet-<role>.service` |
| macOS | `launchd` | `~/Library/LaunchAgents/dev.fleet.<role>.plist`, or `/Library/LaunchDaemons` for system scope |
| Windows admin | Service Control Manager | `fleet-admin` service registered with `sc.exe` |
| Windows daemon | Task Scheduler | `fleet-daemon` logon task registered with `schtasks /Create /XML` |
| Other Unix hosts | fallback supervisor | `~/.fleet/<role>/run/supervisor.json` |

All backends expose the same commands: `start`, `stop`, `restart`, `status`,
`logs`, `install-service`, and `uninstall-service`. Use `--mode service` to force
a native service or `--mode supervisor` to force the fallback.

### launchd

The plist runs `fleet <role> run --config <config>` with `RunAtLoad` and
`KeepAlive`. `PATH` is captured at install time so the daemon can find agent
CLIs; reinstall the service after changing it. User-scope LaunchAgents start at
login. System scope writes a LaunchDaemon and requires root.

### Windows service and task

The admin is a normal Windows service. `fleet-admin` accepts a hidden
`--windows-service` flag; in that mode it registers a service control handler
and uses the `windows-service` crate instead of logging to a console. The
installer registers:

```
sc.exe create fleet-admin binPath= "<fleet-admin.exe> --config <config> serve --windows-service" start= auto
sc.exe failure fleet-admin reset= 86400 actions= restart/5000/restart/10000/restart/30000
```

The admin defaults to `LocalSystem`; set `FLEET_SERVICE_USER` and
`FLEET_SERVICE_PASSWORD` in the elevated install shell, or reconfigure with
`sc.exe config`, to use a dedicated account. That account needs the "Log on as a
service" right.

The daemon deliberately does **not** run as a service. A Session 0 service
cannot see the logged-in user's profile, repositories, or agent CLIs, so the
daemon is registered with Task Scheduler as `fleet-daemon`:

- User scope uses a `LogonTrigger` with `InteractiveToken` and
  `LeastPrivilege`, and starts when that user logs on.
- System scope uses a `BootTrigger` running as `SYSTEM`, for deployments where
  the system account owns the workspaces.
- The task runs `fleet-daemon --config <config> serve --windows-task`, allows
  one instance, starts when available, restarts three times at one-minute
  intervals, and has no execution time limit.
- Logs are appended to `<state_dir>/logs/daemon.log`.

Both Windows backends write logs to files because there is no console. Admin
service commands require an elevated shell; a user-scope daemon task can be
created by the logged-in user. Each backend can be tested without Windows: the
task XML renderer, `sc.exe` state parser, and `schtasks` status parser are pure
functions covered by unit tests.

## Checks

Run the same gates locally that CI runs:

```bash
pnpm fmt      # cargo fmt --all plus workspace formatters
pnpm lint     # clippy with -D warnings plus ESLint
pnpm test     # cargo test --workspace plus web typecheck and lint
```

Use `pnpm test:rust` or `pnpm test:web` to run one half. Clippy runs across all
targets, so test-only code is checked too. The web half runs strict TypeScript
and ESLint.

## End-to-end tests

The black-box suite lives in `crates/e2e-tests`. It starts the real
`fleet-admin`, `fleet-daemon`, and `fleet` binaries on ephemeral loopback ports
with an isolated temporary `HOME`, databases, and Git repositories. The suite
spawns host processes directly, so it needs no container runtime, fixed ports,
or `jq`.

| Command | Coverage |
| --- | --- |
| `pnpm e2e` | Smoke, setup, supervisor lifecycle, and Git writes |
| `pnpm e2e:ui` | Playwright browser scenarios against a live stack |
| `pnpm e2e:stress` | Three daemons, six workspaces, and offline/restart recovery |

`pnpm e2e` builds the three binaries first. The suites are marked `#[ignore]`,
so `cargo test --workspace` stays fast and never spawns servers. Artifacts are
kept when a test fails; set `FLEET_E2E_KEEP=1` to keep them on success as well.
Install Chromium once before running the UI suite. The stress suite is
regression coverage for connection isolation and recovery; it is not a
supported multi-machine deployment model. See
[Guides](/guides/operations/) for operating a running deployment.

## Database migrations

Both storage crates embed their migrations at compile time with SQLx
`migrate!`. They are separate sets:

- `crates/admin-storage/migrations/` — organizations, users, machines,
  pairing codes, workspace and session metadata, permission routing, audit.
- `crates/daemon-storage/migrations/` — workspaces, directory index, sessions,
  authoritative transcript tables, permissions, event outbox, and
  acknowledgements.

Each set is append-only. SQLx stores a SHA-384 checksum in `_sqlx_migrations`;
editing an applied migration makes existing databases fail to start. Add a new
numbered file instead of changing an old one, even to fix a comment.

Both databases carry a `storage_meta` row with a `role` value of `admin` or
`daemon`. Opening a database with the wrong role is rejected before any write,
so pointing the admin at the daemon database cannot destroy data. There is no
cross-role opening and no shared schema. The admin owns metadata; the daemon
owns the transcript. See [Storage](/how-it-works/storage/) for the full model.

## Provider smoke checks

The default provider is `mock`: deterministic, in-process, and used by the E2E
suite. Real provider adapters are checked against fixtures so tests never spend
model quota or depend on a developer's installed CLIs.

| Provider | Local integration |
| --- | --- |
| `claude` | `claude -p --input-format stream-json --output-format stream-json --verbose` |
| `codex` | `codex app-server --listen stdio://` |
| `opencode` | The daemon starts `opencode serve` on a private loopback port; set `OPENCODE_SERVER_URL` to reuse an existing server |
| `generic` | A PTY around any terminal-compatible CLI |

Adapter fixtures live next to each adapter under
`crates/daemon-runtime/src/<provider>/fixtures/`. Refresh them when the upstream
protocol changes. One ignored test exercises a real `opencode serve` without
sending prompts; all other tests must stay off real CLIs. Set the default in
`[agent] default_provider` and see [Configuration](/reference/configuration/).

## Data directories

| Path | Purpose |
| --- | --- |
| `~/.fleet/daemon/fleet-daemon.db` | Daemon database: workspaces, transcript, outbox |
| `~/.fleet/daemon/machine.key` | Ed25519 machine key, mode `0600` |
| `~/.fleet/daemon/machine.key.id` | Stable machine id across key rotation |
| `~/.fleet/daemon/machine.key.token` | Per-machine token, mode `0600` |
| `~/.fleet/admin/fleet-admin.db` | Admin database: metadata, users, audit, pairing |

The daemon database is the authoritative transcript store. The admin keeps
session metadata and proxies history from the daemon; it does not mirror turns,
messages, or tool calls. Deleting these files gives a clean slate, but machines
must pair again. A machine deleted through the API records a permanent
revocation and cannot re-pair until an admin unrevokes it.

## Security notes for development

- The admin binary has no built-in default credential. The `pnpm dev` scripts
  pass `dev-token` explicitly; set `FLEET_ADMIN_TOKEN` for anything shared.
- The admin token is for the REST API. It is never accepted on the machine
  WebSocket. Daemons use their per-machine token plus an Ed25519 challenge.
- Production web builds embed no token. A missing token or a `401` shows the
  SPA auth gate instead of sending unauthenticated requests.
- Pass `workspace_id` when creating a session. A bare `cwd` is accepted only
  when it canonicalizes inside a workspace already registered on that machine.
- Machine identity is a key pair plus a token. A key change requires a rotation
  proof signed by the previously pinned key; losing both credentials requires an
  admin revoke and a fresh pairing code.
- Every workspace path passes through `PathPolicy`. Absolute paths, `..`, and
  symlinks that escape the workspace root are denied.
- Deleting a machine records a revocation, disconnects the live socket, and
  stops reconnection. Unrevoke explicitly before pairing it again.
