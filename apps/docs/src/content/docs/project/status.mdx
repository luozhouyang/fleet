The supported scope for the current release is the **single-machine release**:
one `fleet-admin` instance manages one `fleet-daemon`, and that daemon host can
run multiple workspaces and agent sessions. The release is feature-complete and
in hardening. Multi-machine fleets, remote enrollment, high availability, and
multi-tenant operations are roadmap work, not current product commitments.

<Aside type="caution" title="Multi-machine code is groundwork, not a supported topology">
  The organization and role model, the multi-machine stress suite, and the
  connection isolation tests exist as regression coverage for later work. They
  do not mean that operating a fleet is supported today. Pairing, multi-endpoint
  failover, resumable streams across every event class, and connection leases
  are not productized.
</Aside>

## Status at a glance

| Item | Current state |
| --- | --- |
| Milestone | `v0.1.0` single-machine MVP, feature-complete and hardening |
| Supported topology | One `fleet-admin` plus one `fleet-daemon` |
| Workspaces and sessions | Multiple workspaces per daemon, multiple sessions per workspace |
| Persistence | SQLite only; no Redis, NATS, or external database |
| Default provider | `mock`, deterministic and used by the end-to-end tests |
| Real providers | Claude Code CLI, Claude Code ACP, Codex app-server, OpenCode server, generic PTY |
| Web UI | SPA served by `fleet-admin` over REST and WebSocket |
| Management entry points | Browser SPA, `fleet` CLI, and the admin REST API |
| Deployment | Local host or LAN; terminate TLS in front of the admin in production |

Single-machine does not mean single-workspace. One daemon can register several
workspaces, and each workspace can host several sessions. They share the host's
filesystem, Git repositories, and agent processes.

## Deliberately deferred

These are out of scope for the single-machine release. Some have groundwork in
the repository; none are supported operations yet.

- **Multi-instance admin.** No Redis or NATS routing, connection leases, or
  shared state across admin processes.
- **Remote and offline enrollment.** Pairing codes require the daemon to reach
  the admin at enrollment time. Deferred enrollment for unreachable machines is
  not implemented.
- **QR codes, OAuth device flow, and UI pairing.** Enrollment is CLI-driven and
  same-host or same-LAN only.
- **Git push, merge, rebase, and history rewriting.** Reads, diffs, and
  stage/commit/checkout are supported; publishing and rewriting are not.
- **Remote file editing.** The browser viewer is read-only.
- **Agent sandboxing.** Agent processes are not confined by the daemon beyond
  workspace path policy and normal process management.
- **Organization and user administration UI.** Roles and organizations exist in
  the API and CLI; the browser has no admin console for them.
- **OpenCode structured diffs and image attachments.** Text streaming, tools,
  and permissions are mapped; structured diffs and images are not.
- **Worktree orchestration and UI component unit tests.** Parallel worktree
  management and a component-level test suite remain future work.

User question support is declared per provider through
`AgentCapabilities.user_questions`: the mock, Codex, OpenCode, and Claude ACP
adapters advertise it, while the Claude CLI and generic PTY adapters do not.
Permission and question payloads are live-only: the admin proxies them and does
not persist their content, so they are absent after a machine goes offline.

The per-IP upgrade limiter is in-memory, resets on admin restart, and is not
shared across admin instances. Per-code attempt limits are durable.

## Roadmap

| Version | Focus | Exit signal |
| --- | --- | --- |
| `v0.2` | Single-machine hardening: installer and upgrades, real-provider conformance, token lifecycle, first-run experience, observability, UI tests | A new user installs on a clean host and reaches a Git commit within ten minutes; upgrade and backup are verified |
| `v0.3` | Multi-machine foundation: operable enrollment, multiple endpoints and failover, resumable streams, proxy and TLS support, fleet UI, capacity tests | Ten machines across two LANs reconnect independently and converge without cross-machine leakage |
| `v0.4` | Remote access: Tailscale, Cloudflare Tunnel, generic reverse proxy, site relay, discovery, connection-quality monitoring | Reproducible NAT, corporate-proxy, and isolated-LAN deployments with E2E coverage |
| `v0.5` | Teams and tenancy: organization UI, invitations, SSO/OIDC, token expiry, quotas, isolation tests | Two organizations share one admin with isolated resources, events, audits, and quotas |
| `v1.0` | Scale and collaboration: multi-agent and worktree orchestration, session replay and templates, provider plugin model, multi-instance storage, sandboxing | Production deployment, upgrade, backup, capacity, and failure drills pass |

The current hardening queue is real-provider conformance, signed and notarized
release artifacts, upgrade verification, token expiry and rotation UI, first-run
and accessibility work, observability, and broader UI test coverage.

### Out of scope

A hosted multi-tenant SaaS, a mobile app, a full browser IDE, arbitrary Git
subcommands or force-push, a daemon that listens on a public inbound port, and an
unaudited plugin marketplace are not on this roadmap. They would be evaluated
separately after the remote-access work.

## Verification entry points

```bash
pnpm test         # Rust workspace tests plus web typecheck and lint
pnpm e2e          # smoke, setup, supervisor lifecycle, and Git writes
pnpm e2e:ui       # Playwright browser scenarios against a live stack
pnpm e2e:stress   # three daemons, six workspaces, offline and restart recovery
```

A milestone is complete only when its tests, end-to-end coverage, and documented
exit criteria pass together. Merged code alone is not a completion signal. See
[Development](/project/development/) for the harness details and
[Operations](/guides/operations/) for running a deployment.
