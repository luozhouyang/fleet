Fleet is one Cargo workspace with three library domains — shared core, admin,
and daemon — plus thin application entrypoints. The split exists to keep
privileges and failure domains separate. The admin never touches a repository,
the daemon never serves the browser, and the protocol crate never performs I/O.

## Dependency graph

`fleet-core-common`; those edges are omitted for readability.

## Ownership

| Crate | Owns |
| --- | --- |
| `fleet-core-common` | IDs, timestamps, `ApiError`, pagination, and shared logging primitives |
| `fleet-core-protocol` | Wire DTOs for agent, workspace, Git, machine, connection, pairing, RPC, and authorization types |
| `fleet-core-auth` | Ed25519 machine identity, challenge nonces, bearer-token checks, pairing-code and per-machine token helpers |
| `fleet-core-config` | `AdminConfig` and `DaemonConfig`: defaults, TOML loading, `FLEET_*` overrides, path resolution |
| `fleet-core-connection` | Reverse WebSocket gateway and client, handshake, connection registry, RPC correlation, reconnect, pairing client |
| `fleet-admin-storage` | Admin SQLite database, migrations, and repositories for machines, organizations, users, pairing codes, metadata, permissions, and audit |
| `fleet-admin-machine` | In-memory machine registry backed by durable metadata and last-seen state |
| `fleet-admin-eventbus` | In-process publish/subscribe and filtered subscriptions for browser fan-out |
| `fleet-daemon-storage` | Daemon SQLite database, migrations, authoritative transcript, workspace index, sessions, permissions, outbox, and acknowledgements |
| `fleet-daemon-process` | Managed child processes, PTY processes, process groups, bounded output, and captured commands |
| `fleet-daemon-runtime` | Provider trait and registry, session state machine, event emitter, permission hub, and the `mock`, `claude`, `codex`, `opencode`, and `generic` adapters |
| `fleet-daemon-workspace` | Workspace registry, `PathPolicy`, lazy directory listings, ETag reads, search, ignore rules, and the file watcher |
| `fleet-daemon-git` | Git discovery, status, diffs, summaries, branches, log, and validated write operations |
| `fleet-e2e-tests` | Black-box host-process harness and the `#[ignore]`d smoke, setup, lifecycle, Git-write, UI, and multi-machine suites |

The TypeScript side mirrors the same separation. `packages/protocol-types` holds
generated or hand-maintained API types, `packages/api-client` wraps the REST and
event surfaces, and `packages/ui` holds shared React components. `apps/web` is
the only browser application.

## Boundaries

These rules keep the graph acyclic and the trust boundaries meaningful.

- **`core-protocol` has DTOs only.** It defines the connection envelope, RPC
  method names, event payloads, and domain types. It performs no I/O, opens no
  sockets, and depends on no implementation crate.
- **Only `admin-storage` and `daemon-storage` open SQLite.** They also own
  their migration sets. They share protocol models, never tables or repository
  code. A `storage_meta` role marker rejects the wrong database before any
  write.
- **Only `daemon-git` runs `git`.** It uses argv-only invocation, bounded
  output, and timeouts, and validates paths and branch names before a write.
- **Only `daemon-runtime` spawns agents,** and it does so through
  `daemon-process`. Process group cleanup, PTY handling, and output bounds live
  in the process crate, not in adapters.
- **Only the admin proxies RPCs.** `fleet-admin` forwards typed requests over
  the live machine socket. It does not read files, execute Git, or start agents.
- **`daemon-workspace` and `daemon-git` do not depend on each other.**
  `daemon-runtime` does not depend on either. A session uses a workspace path; it
  does not need the Git service to run.
- **`core-connection` has no concrete provider adapter.** It transports
  envelopes and frames; provider behavior stays in `daemon-runtime`.
- **`admin-eventbus` is admin-domain only.** It fans platform events out to
  browser subscribers. The daemon does not depend on it.

## Applications are thin entrypoints

`apps/fleet-admin` and `apps/fleet-daemon` expose a library `run` function. Their
binaries parse process-level flags such as `--config` and `serve`, build the
configuration, and call the library. Server assembly, migrations, shutdown, and
readiness live in the library or its crates.

`apps/fleet-cli` is the user-facing `fleet` binary. It does not link the admin or
daemon server crates. It resolves the server binaries, starts them as child
processes, or delegates lifecycle commands to systemd, and it wraps the admin
REST API. That keeps the CLI installable without pulling the server dependency
tree into every host.

`apps/web` is a static SPA. It talks to the admin over REST and a browser
WebSocket, and it depends only on the shared TypeScript packages.

When adding code, place it by ownership: a new wire type in
`core-protocol`, admin persistence in `admin-storage`, a machine registry change
in `admin-machine`, a provider in `daemon-runtime`, a filesystem capability in
`daemon-workspace`, a Git operation in `daemon-git`, and transport behavior in
`core-connection`.
