Authentication answers "is this really machine X?". Registration answers a
different question: "what does the control plane know about X, and who is
allowed to use it?"

These happen in sequence. The gateway completes the handshake first, then emits
`GatewayEvent::MachineConnected`. The admin's event consumer takes over from
there.

<pre class="mermaid">{`
flowchart TD
  A["GatewayEvent::MachineConnected"] --> B["ensure_machine_org<br/>build MachineRegistration"]
  B --> C{"handshake verified<br/>key + token?"}
  C -->|"yes"| D["MachineRegistry::register_or_update<br/>SQLite upsert + cache · Online"]
  C -->|"no"| X["never emitted:<br/>handshake rejected first"]
  D --> E["publish machine.status<br/>and connection.state"]
  E --> F["refresh_machine_snapshot()<br/>providers.list + workspaces.list"]
  F --> G["persist workspace snapshots<br/>refresh machine metadata"]
`}</pre>

## What gets registered

`register_machine` builds a `MachineRegistration` from the `hello` payload plus
whatever the admin already knew:

| Field | Source |
| --- | --- |
| `machine_id` | `hello.machine_id` |
| `public_key` | `hello.public_key` — must match the pinned key |
| `name`, `hostname`, `os`, `arch` | `hello` |
| `daemon_version`, `protocol_version` | `hello` |
| `providers` | Previous snapshot at first, refreshed asynchronously |
| `workspaces` | Previous snapshot at first, refreshed asynchronously |

`MachineRegistry::register_or_update` validates the id and key, refuses a key that
differs from the pin, then upserts the row into SQLite and updates the warm
in-memory cache. The machine is marked `Online`, with `connected_at` and
`last_seen_at` set to the current time.

The admin publishes two platform events immediately:

- `machine.status` with the updated `Machine` record, for the dashboard.
- `connection.state` with `machine_id`, `connection_id`, and `state: online`, for
  connection indicators.

## The snapshot refresh

Registration must not block the event consumer: a reconnect storm would overflow
the gateway event channel. So the initial record reuses the previous snapshot,
and a background task asks the daemon for the current one:

1. `providers.list` → provider ids, capabilities, and status.
2. `workspaces.list` → workspace summaries.
3. Each workspace is upserted into SQLite.
4. The machine row is updated with the fresh counts.

The requests use a short timeout (clamped between 500 ms and 5 s). A failed
snapshot is logged and ignored; the previous snapshot stays visible.

<Aside type="caution" title="Stale snapshots cannot overwrite the live connection">
  Before applying a late snapshot, the admin compares the connection id that
  produced it with the current live connection id. If a reconnect replaced the
  socket in the meantime, the late result is dropped. The same guard exists for
  disconnect events, which is why a machine does not briefly flicker offline
  during a fast reconnect.
</Aside>

## Going offline

When the socket ends, the gateway emits `MachineDisconnected`. The admin checks
the live registry first:

- If a replacement connection is already live, the event belongs to the old
  socket and is ignored.
- Otherwise the machine is marked `Offline`, `last_seen_at` is updated, and
  `machine.status` is published.

A heartbeat gap follows the same path: after the configured timeout the admin
closes the socket, and the normal disconnect handling runs.

## Binding a machine to an organization

Cryptographic identity is global: a machine id is the same everywhere. Access is
not. The admin binds machines to organizations through the `machine_orgs` table:

- Pairing writes the code's organization to `machine_orgs` in the same
  transaction that pins the key. Connecting without a prior pairing falls back
  to `ensure_machine_org(machine_id, DEFAULT_ORG_ID)` with insert-if-absent
  semantics.
- An administrator can move a machine with
  `PUT /api/v1/machines/{id}/org`; the route checks that the target organization
  exists and that the caller may manage it.
- The event indexes cache the machine → organization mapping so browser event
  fan-out does not hit SQLite for every message.

<pre class="mermaid">{`
flowchart TD
  M["machine"] --> O["organization"]
  U["user"] -->|"role: admin / member / viewer"| O
  W["workspace"] --> M
  S["session"] --> M
  P["permission request"] --> S

  O --> V1["visible machines"]
  M --> V2["visible workspaces"]
  M --> V3["visible sessions"]
`}</pre>

Authorization inherits upward from the resource that owns the data:

- **workspace → machine**
- **session → machine**
- **permission request → session → machine**
- **machine → organization**

A user token is scoped to one organization. Cross-organization lookups return
`404` rather than `403`, so a caller cannot probe which ids exist elsewhere. The
legacy shared admin token is the exception: it behaves as a super-admin and sees
every organization.

## Removing a machine

`DELETE /api/v1/machines/{id}` is a permanent revocation. It records the machine
id in `machine_revocations`, disconnects the live socket, and removes the
machine and its dependent rows (workspaces, sessions, turns, messages,
permissions) from active storage. A revoked daemon is rejected during the
handshake and stops reconnecting instead of entering its backoff loop. The
pinned public key goes with the row.

Revocations are visible at `GET /api/v1/machines/revoked`. An admin can restore
pairing with `POST /api/v1/machines/{id}/unrevoke` (or
`af machines unrevoke <id>`). A revoked machine cannot pair again — even with a
fresh code — until it is unrevoked. Unrevocation restores the pinned key but not
the credential: revocation destroyed the stored token, so the machine must pair
again with a fresh code. An existing `<key_file>.token` is rejected with HTTP
401 until then. Pairing a different key still requires the old key's rotation
proof.

<Aside type="note" title="What survives a reconnect">
  Reconnecting is not re-registering from the admin's point of view. The machine
  id is stable, the pinned key is reused, the organization binding is untouched,
  and only the live connection id changes. The snapshot refresh then reconciles
  provider and workspace changes.
</Aside>
