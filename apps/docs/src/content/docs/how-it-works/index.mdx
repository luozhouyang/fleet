Agent Fleet splits responsibilities between two long-lived processes:

- **`fleet-admin`** is the control plane. It serves the web UI and REST API,
  authenticates users, authorizes requests, and keeps durable machine metadata.
- **`fleet-daemon`** runs on each machine. It owns agent processes, workspaces,
  and Git access — the things that must happen on the host itself.

The two sides are not connected by inbound traffic to the machine. Instead, each
daemon opens a single outbound WebSocket to the control plane and keeps it open.
That reverse connection carries both directions of the protocol: the admin sends
requests down it, and the daemon sends events and heartbeats up it.

## The shape of the system

Three properties explain most of the design:

1. **Machines dial out, never listen.** A daemon works behind NAT, a firewall, or
   a laptop lid without any port forwarding. The only local listener is a
   loopback health endpoint.
2. **Enrollment is explicit, credentials are per machine.** The first connection
   redeems a single-use pairing code and the admin issues a per-machine token.
   Every later connection presents that token; a per-machine Ed25519 key proves
   *which* machine is connecting. Neither credential alone is sufficient.
3. **Identity is pinned during enrollment.** Pairing pins the public key after
   the machine proves possession of it. Later key changes require a proof signed
   by the previously pinned key; trust-on-first-use is not used.

## Data at a glance

| Data | Lives in | Lifetime |
| --- | --- | --- |
| Live sockets | `ConnectionRegistry` in `fleet-admin` memory | Process lifetime |
| Machine metadata | SQLite via `MachineRegistry` | Durable |
| Ed25519 key pair | `~/.fleet/daemon/machine.key` on the machine | Durable |
| Machine id | `<key_file>.id` | Durable across key rotation |
| Providers and workspaces | SQLite snapshot, refreshed on reconnect | Durable, best-effort |

<Aside type="note" title="The control plane never touches the filesystem">
  `fleet-admin` does not read files, run agents, or execute Git on a machine. It
  forwards typed RPCs over the live socket, and the daemon performs the work.
  That boundary is why the machine token and the per-machine key can stay
  independent of user authentication.
</Aside>
