Every daemon keeps one WebSocket open to the admin at `/ws/machine`. The daemon
is always the client: it opens the connection, authenticates, and reconnects
after failures. The admin never dials a machine.

This direction matters. It means a machine needs outbound HTTPS/WSS only, and
there is no inbound listener to expose, firewall, or port-forward. The daemon's
local health server stays bound to loopback.

## Configuration

The daemon reads its target from `[connection]` in `config.toml` or from the
environment:

| Daemon setting | Environment variable | Meaning |
| --- | --- | --- |
| `connection.server_url` | `AGENT_FLEET_SERVER_URL` | WebSocket URL, e.g. `ws://127.0.0.1:8787/ws/machine` |
| `connection.pairing_code` | `AGENT_FLEET_PAIR_CODE` | Optional one-shot code for automated provisioning (not written by `af setup`) |
| `machine.name` | `AGENT_FLEET_MACHINE_NAME` | Display name sent in `connection.hello` |

The per-machine token is not a configuration setting. After `af setup` or
`fleet-daemon pair`, the daemon reads it from `<key_file>.token` (mode `0600`,
group/world-readable files are rejected) and presents it as
`Authorization: Bearer <machine-token>` on every upgrade. There is no
`connection.token` and no machine-token environment variable.

On the admin side the relevant settings are:

| Admin setting | Environment variable | Meaning |
| --- | --- | --- |
| `auth.admin_token` | `AGENT_FLEET_ADMIN_TOKEN` | Token for the REST API and user authentication |
| `auth.pair_code_ttl_secs` | `AGENT_FLEET_PAIR_CODE_TTL` | Pairing-code lifetime (default 600 seconds) |
| `auth.pair_code_max_attempts` | — | Failed handshakes per code (default 5) |

<Aside type="caution" title="Enroll instead of configuring a shared token">
  The admin token is never accepted on `/ws/machine`. Create a code with
  `af machines pair-code` (or let `af setup` do it) and redeem it once; the
  daemon stores the resulting per-machine token next to its key. There is no
  shared-token fallback, no trust-on-first-use and no key-only mode.
</Aside>

If `connection.server_url` is missing, the daemon starts in local-only mode: it
runs workspaces and agents, but never connects to a control plane. If the URL is
set but `<key_file>.token` is absent and no pairing code is configured, the
handshake is rejected with `machine_not_paired` and the client stops rather than
retrying forever.

## One envelope for everything

The wire format is WebSocket text frames carrying JSON. Every frame uses the same
`ConnectionEnvelope` shape (`crates/core-protocol/src/connection/envelope.rs`):

| Field | Purpose |
| --- | --- |
| `version` | Protocol version; mismatches are rejected during `hello` |
| `stream_id` | Logical stream (`default`, `events`, or `rpc/<method>`) |
| `message_id` | Correlation id for requests, responses, and errors |
| `type` | `request`, `response`, `event`, or `error` |
| `method` / `event` | RPC method name, or event name for `type: event` |
| `sequence` | Per-connection ordering for events, used for gap detection |
| `cursor` | Outbox sequence of a durable `agent.event`; the admin acknowledges this exact sequence |
| `payload` | Method- or event-specific JSON |

Large payloads can be split into `StreamFrame`s, but the MVP does not use binary
frames.

## Who can send what

<pre class="mermaid">{`
sequenceDiagram
  autonumber
  participant A as agent-admin
  participant D as agent-daemon

  A->>D: request · method + message_id
  D-->>A: response or error · same message_id
  D->>A: event · name + sequence
  D->>A: heartbeat · sequence

  Note over A: ConnectionRegistry resolves responses<br/>Event pipeline consumes GatewayEvents
`}</pre>

- **Admin → daemon** — only `request` frames. A request names a method such as
  `workspaces.list`, `sessions.create`, or `git.commit`.
- **Daemon → admin** — `response` or `error` frames carrying the same
  `message_id`, plus `event` frames for agent output, workspace changes, Git
  status, and permission requests.
- **Both → each other** — control events. The admin can send
  `connection.disconnect`; the daemon emits `connection.closed` when the socket
  ends.

The daemon's `DaemonHandler` dispatches every admin request to local services and
returns typed errors as `ApiError`; the admin's `ConnectionRegistry::request`
holds a `oneshot` sender keyed by `message_id` and resolves the matching
response.

## Heartbeats and liveness

Both sides run timers:

- The daemon sends `connection.heartbeat` on the configured interval (default
  `15s`). Each heartbeat has its own sequence number.
- The gateway acknowledges it and emits `GatewayEvent::Heartbeat`, which the admin
  turns into a `last_seen_at` update (`MachineRegistry::touch`).
- The admin closes a connection after `machines.heartbeat_timeout_ms` without
  inbound traffic (default `45s`).
- The daemon runs its own stale-connection monitor and drops a socket after
  `max(3 × heartbeat_interval, 45s)` with no inbound traffic.

  [*] --> Disconnected

## Reconnects are normal

The client loop backs off exponentially from `500ms` to `30s` with jitter. A
connection that stayed up for more than 30 seconds resets the backoff to its
initial value.

The admin treats a reconnect as a replacement connection, not a second machine:

- `ConnectionRegistry::insert` swaps the handle and cancels the old connection.
- A stale disconnect event from the replaced socket is ignored while a newer
  connection is live, so the machine does not flicker offline.
- Durable agent events are not lost while disconnected. Their projection rows
  and outbox entries commit in one daemon transaction. Each frame carries its
  own outbox sequence; the admin acknowledges every applied sequence, and
  storage keeps out-of-order acknowledgements until the gap is filled. Any
  sequence that is not acknowledged is replayed until it is.
- Ephemeral events (streaming deltas, raw provider frames) are live-only and are
  dropped while disconnected. The final message/tool event restores the
  authoritative state.
- On reconnect the admin also asks for a fresh provider and workspace snapshot
  and reconciles its durable metadata.

Requests to an offline machine fail fast with the `machine_offline` error code;
the admin does not queue them.

<Aside type="tip" title="Why the socket is the source of liveness">
  The admin's SQLite row says `Online` or `Offline`, but the registry of live
  sockets is the authority. A machine can be present in the database and still
  be unreachable, which is why proxied requests check the registry first and
  return `machine_offline` instead of waiting for a timeout.
</Aside>
