Opening the WebSocket is only the transport step. Before the admin routes a
single request to a daemon, the daemon must prove two things:

1. It holds the **per-machine token** issued during enrollment (every connection
   after the first). The very first connection instead redeems a short-lived
   **pairing code**.
2. It holds the **private key** for the machine id it claims.

Neither a token nor a code alone is enough: the daemon also signs a fresh
challenge with its Ed25519 key. There is no shared machine token and no
trust-on-first-use path.

<pre class="mermaid">{`
sequenceDiagram
  autonumber
  participant D as fleet-daemon
  participant A as fleet-admin
  participant R as MachineRegistry

  alt first connection (pairing)
    D->>A: WS upgrade (no credential)
    D->>A: connection.hello<br/>machine_id, public_key, pairing_code
    A->>A: validate code (TTL, attempts, org)
  else later connections (token)
    D->>A: WS upgrade + Authorization: Bearer machine-token
    D->>A: connection.hello<br/>machine_id, public_key
    A->>A: hash(token) -> machine_id, check pin
  end

  A->>R: pinned_key(machine_id)
  R-->>A: pinned key or none
  A->>D: connection.auth_challenge<br/>challenge_id, nonce

  D->>D: sign nonce with Ed25519 private key
  D->>A: connection.auth<br/>signature, optional rotation proof

  A->>A: verify_strict(public_key, nonce, signature)
  alt changed key
    A->>A: verify old key signed the rotation statement
  end

  alt pairing
    A->>R: consume code + pin_key + record token hash
    A-->>D: connection.accepted<br/>machine_token, org_id, heartbeat_interval_ms
    D->>D: write <key_file>.token (0600)
  else token
    A-->>D: connection.accepted<br/>connection_id, heartbeat_interval_ms
  end

  A->>R: registry.insert(machine_id to ConnectionHandle)
  A-->>A: GatewayEvent::MachineConnected
`}</pre>

## Step by step

1. **Enrollment code.** An admin calls `POST /api/v1/pairing/codes`,
   `fleet admin machines pair-code`, or `fleet daemon setup`. The admin stores only
   `SHA-256(normalize(code))` and returns the plaintext once. Codes are bound to
   an organization, expire after `auth.pair_code_ttl_secs` (default 600
   seconds) and allow `auth.pair_code_max_attempts` (default 5) failures.
2. **Upgrade.** In token mode the daemon sends
   `Authorization: Bearer <machine-token>` (the token issued by a previous
   pairing, not the REST admin token). In pairing mode it sends no credential
   and puts the code in `connection.hello`.
3. **`connection.hello`.** The first frame must be a `request` with method
   `connection.hello`. It carries `machine_id`, display name, hostname, OS,
   architecture, daemon version, protocol version, the base64 Ed25519 public
   key, and the optional `pairing_code`. The code is redacted from logs.
4. **Mode resolution and validation.** The admin rejects an empty id or key and
   an unknown protocol version. An unpaired machine without a code gets
   `machine_not_paired`; a pinned machine without a token gets
   `machine_token_required`; an invalid, expired, used or attempt-exhausted code
   gets `pairing_code_invalid`. A revoked machine id is rejected before the code
   is examined. The whole handshake has a 10-second deadline.
5. **`connection.auth_challenge`.** The admin generates a fresh 32-byte random
   nonce, a `challenge_id`, and a 60-second expiry. Nothing is pinned yet — an
   unauthenticated `hello` must not be able to poison a machine id.
6. **`connection.auth`.** The daemon signs the raw nonce bytes with its private
   key and returns the base64 signature. If it rotated its key, it also returns
   a `KeyRotationProof` signed by the previously pinned key.
7. **Verification.** The admin verifies the signature against the public key
   from `hello` using `verify_strict` semantics. In pairing mode a bad signature
   records a failed attempt and returns a terminal `pairing_code_invalid` error
   frame without consuming the code. A changed key additionally requires a valid
   rotation proof; otherwise the admin sends a `machine_key_mismatch` error
   frame before closing.
8. **Pairing completion.** Only after every check passes does one transaction
   consume the code, pin the key, record the machine/organization and store the
   token hash. `connection.accepted` returns `machine_token` and `org_id`. The
   daemon writes the token to `<key_file>.token` with mode `0600`.
9. **`connection.accepted`.** The gateway inserts `machine_id → ConnectionHandle`
   into the in-memory registry and returns the connection id plus the heartbeat
   interval. The `MachineConnected` event then starts the registration pipeline.

## Machine identity on disk

| Item | Path | Notes |
| --- | --- | --- |
| Ed25519 private key | `~/.fleet/daemon/machine.key` | JSON key file, mode `0600`; group/world-readable files are rejected |
| Machine id | `<key_file>.id` | Stable across key rotation; defaults to `m_<sha256(public_key)>` |
| Per-machine token | `<key_file>.token` | Written after pairing, mode `0600`; never stored in the daemon TOML |
| Previous key | `<key_file>.previous` | Only present between `rotate-key` and the next successful handshake |

The private key and token never leave the machine. The admin stores only the
public key and a hash of the token.

<Aside type="note" title="Why the id is stored separately">
  If the machine id were recomputed from the public key on every start, rotating
  the key would silently create a new machine with no workspaces and no history.
  Persisting `<key_file>.id` keeps the identity — and its organization binding —
  stable across rotation.
</Aside>

## Key rotation

A key change is not accepted just because the new key can sign. The daemon must
prove the old key authorized the change:

<pre class="mermaid">{`
sequenceDiagram
  autonumber
  participant D as fleet-daemon
  participant A as fleet-admin

  Note over D: daemon stopped
  D->>D: rotate-key writes new machine.key<br/>and keeps machine.key.previous

  D->>A: WS upgrade + machine token
  D->>A: connection.hello with new public key
  A->>A: pinned key differs, rotation required
  A->>D: connection.auth_challenge nonce
  D->>A: connection.auth<br/>new-key signature + RotationProof

  A->>A: verify new key signed nonce
  A->>A: verify old key signed rotation statement
  A->>A: pin the new key
  A-->>D: connection.accepted
  D->>D: delete machine.key.previous
`}</pre>

The rotation statement is canonical and binds the machine id, the new public key,
and the current nonce:

```text
agent-fleet-key-rotation-v1
machine_id=<id>
new_public_key=<base64 key>
nonce=<base64 nonce>
```

Because the nonce is fresh for every handshake, a captured proof cannot be
replayed in a later connection. If verification fails, the existing pin is left
untouched and the daemon stays rejected until it presents a valid proof. The
per-machine token in `<key_file>.token` stays valid across rotation.

## What this protects — and what it does not

Pairing and the per-machine token protect against:

- **Shared-secret compromise.** There is no fleet-wide machine token; stealing
  one machine's token does not enroll or impersonate another machine.
- **Token leakage alone.** A stolen token cannot impersonate an existing
  machine, because the attacker does not have its private key.
- **Key substitution.** A new key is accepted only with a rotation proof from
  the previously pinned key.
- **Replay.** Each challenge nonce is single-use and expires after 60 seconds;
  pairing codes are single-use and attempt-limited.
- **Pin poisoning.** The key is pinned only after proof of possession, not from
  the unauthenticated `hello` frame.
- **Code enumeration.** Unknown, expired, used and locked codes are all reported
  as `pairing_code_invalid`.

Current limitations:

- Enrollment is implemented for same-host / same-LAN deployments. Remote or
  offline enrollment, QR bootstrap, OAuth device flow and UI pairing are future
  work.
- Upgrade throttling is in-memory and per source IP, and only unauthenticated
  (pairing) upgrades are charged; authenticated token reconnects are not
  throttled. It resets on restart and is not shared across admin instances.
  Per-code attempt limits are stored with the code and survive restarts.
- Re-pairing with a different key requires the old key's rotation proof. A
  revoked machine cannot re-pair until an admin unrevokes it.

<Aside type="danger" title="Treat the pairing code and token as credentials">
  Serve the admin over TLS (`wss://`) outside loopback. Pairing codes are shown
  once — do not paste them into shell history, logs or URLs that get indexed.
  The token file is mode `0600`; the daemon refuses a group/world-readable token.
</Aside>
