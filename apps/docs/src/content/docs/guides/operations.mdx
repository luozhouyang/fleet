The admin and daemon are long-lived services. Routine operations are mostly
read-only checks, followed by a targeted restart or a backup before an upgrade.

## Goal

Know whether both roles are healthy, manage them under the native service
manager or the fallback supervisor, find their logs, and upgrade without losing
data.

## Prerequisites

- Fleet installed on the host. See [Installation](/getting-started/installation/).
- Access to the role configuration paths, normally `~/.fleet/admin/config.toml`
  and `~/.fleet/daemon/config.toml`.
- The ability to authenticate sudo once (Unix) or approve UAC (Windows) when a
  command writes or controls the system service definitions. There is no scope
  selector: configuration and state are always under `~/.fleet`, and the
  services run as you.

## Steps

<Steps>
  <Step title="Check status">
    ```bash
    fleet status
    ```

    The command summarizes both roles and exits with a meaningful code:

    | Exit | Meaning |
    | --- | --- |
    | `0` | Both roles are healthy |
    | `1` | At least one role is stopped |
    | `2` | At least one role is degraded or unhealthy |

    Per-role checks are also available:

    ```bash
    fleet admin status
    fleet daemon status
    fleet admin health
    ```
  </Step>

  <Step title="Run the diagnostic">
    ```bash
    fleet doctor
    ```

    `doctor` is read-only. It inspects configuration, paths, permissions, ports,
    database roles, and process state, and prints `WARN` or `FAIL` findings with
    a suggested fix. It exits `1` when any check is `FAIL`; warnings do not
    change the exit code.
  </Step>

  <Step title="Start, stop, or restart a role">
    ```bash
    fleet admin start
    fleet admin restart
    fleet admin stop
    fleet daemon restart
    ```

    Add `--mode auto|systemd|supervisor` to force a process manager. `auto`
    prefers systemd when a unit is installed and available, and falls back to
    the built-in supervisor otherwise. Use `--timeout` to extend the shutdown or
    startup wait.
  </Step>

  <Step title="Read logs">
    ```bash
    fleet admin logs -f -n 200
    fleet daemon logs -n 200
    ```

    With systemd, logs come from journald. launchd services and both Windows
    backends write log files under the role state directory. In supervisor mode, Fleet reads the
    role's log file; `--supervisor` shows the supervisor log instead. Pass
    `--mode service` or `--mode supervisor` when auto-detection picks the wrong
    source.
  </Step>

  <Step title="Install or remove services">
    Preview the change first, then install:

    ```bash
    fleet admin install-service --dry-run
    fleet admin install-service --yes
    fleet daemon install-service --yes
    ```

    Fleet installs a systemd system unit on Linux or a LaunchDaemon on macOS;
    both run as the invoking user. On Windows, both roles become Task Scheduler
    startup tasks with a stored credential. The commands ask for sudo once on
    Unix and require UAC elevation on Windows. On hosts without a native
    manager, Fleet uses its fallback supervisor. Remove the installed service
    with `uninstall-service`:

    ```bash
    fleet admin uninstall-service --yes
    fleet daemon uninstall-service --yes
    ```

    <Aside type="caution" title="Never run two supervisors">
      Do not leave a foreground `run` command, a supervisor, and a native service
      managing the same role at once. Stop the extra process before starting
      another, and use `--mode` to make the intended manager explicit.
    </Aside>
  </Step>

  <Step title="Upgrade or remove Fleet">
    `fleet upgrade` downloads the release archive that matches this machine,
    verifies it against `SHA256SUMS`, replaces the three binaries and the web
    assets next to the running `fleet`, and restarts any installed services.
    Configuration and data are preserved. After the restart it waits for
    `/api/v1/ready`; if a service does not become ready, it restores the previous
    binaries and web assets and restarts them.

    ```bash
    fleet upgrade --dry-run
    fleet upgrade --version v0.2.2 --yes
    ```

    Use `--no-restart` to replace files without touching running services, and
    `--force` to reinstall the current version. The binaries live under your
    home and are replaced without elevation; restarting a system service asks
    for sudo (or UAC on Windows).

    `fleet uninstall` removes services, the watchdog, and installed binaries.
    Data is kept by default; pass `--delete-data` (or `--purge`) to remove
    configuration, databases, keys, and secrets as well:

    ```bash
    fleet uninstall --dry-run
    fleet uninstall --yes                 # keep data
    fleet uninstall --delete-data --yes   # remove everything
    ```
  </Step>

  <Step title="Back up before changes">
    Configuration edits made by Fleet create a `.bak` file next to the original.
    `fleet upgrade` keeps the previous binaries and web assets as `.old-*`
    files until the restarted services pass readiness, then removes them.

    It does not back up databases or configuration. Back those up separately
    before an upgrade, ideally while the role is stopped or with SQLite's online
    backup command. The admin database and daemon database are separate files
    with different roles.

    Data directories are created with mode `0700` and sensitive files with
    `0600`. Keep it that way; `fleet doctor` reports permission problems.
  </Step>

  <Step title="Upgrade">
    Rebuild or install the new binaries, then re-run the installer:

    ```bash
    fleet admin install-service --yes
    fleet daemon install-service --yes
    fleet admin restart
    fleet daemon restart
    ```

    After the restart, run `fleet status` and `fleet doctor`. If a role starts
    with an unexpected database or role error, stop and restore the matching
    database rather than pointing both roles at one file.
  </Step>
</Steps>

## Configuration commands

```bash
fleet config show
fleet config validate
fleet config path

fleet admin config show
fleet admin config path
fleet admin config validate

fleet daemon config show
fleet daemon config path
fleet daemon config validate
```

`fleet config` manages the CLI configuration, including the admin URL and token.
The role-scoped `config` commands inspect the service configuration. Use
`--reveal` with `admin config show` only on a trusted terminal.

## Metrics

Both roles expose Prometheus text metrics on loopback listeners. No external
service is required, and neither endpoint is part of the public API.

| Role | Default endpoint | Listener |
| --- | --- | --- |
| Admin | `http://127.0.0.1:9101/metrics` | Dedicated metrics listener (`[metrics]`) |
| Daemon | `http://127.0.0.1:18080/metrics` | Existing health listener (`[daemon] host`/`port`) |

The admin listener is enabled by default. Disable it or move it with the
`[metrics]` section, or with `FLEET_METRICS_ENABLED`, `FLEET_METRICS_HOST` and
`FLEET_METRICS_PORT`:

```toml
[metrics]
enabled = true
host = "127.0.0.1"
port = 9101
```

```bash
FLEET_METRICS_ENABLED=false fleet admin restart
FLEET_METRICS_PORT=9102 fleet admin restart
```

A bind failure aborts admin startup with an error naming the metrics address,
so a port conflict is visible immediately instead of leaving a silently
missing endpoint. The daemon always serves `/metrics` on its health listener;
the health JSON at `/health` and `/api/v1/health` is unchanged.

<Aside type="caution" title="Keep the listeners on loopback">
  Both endpoints are unauthenticated and bind to `127.0.0.1` by default.
  Exposing them requires a reverse proxy that terminates TLS, enforces network
  policy, and adds its own access control. Do not bind them to a public
  interface. Labels never contain user names, machine ids, session ids, paths,
  tokens, or raw URLs; HTTP route labels are matched route templates.
</Aside>

### Prometheus scrape configuration

```yaml
scrape_configs:
  - job_name: fleet-admin
    static_configs:
      - targets: ["127.0.0.1:9101"]
  - job_name: fleet-daemon
    static_configs:
      - targets: ["127.0.0.1:18080"]
```

### Metric reference

| Metric | Type | Labels | Meaning |
| --- | --- | --- | --- |
| `fleet_admin_build_info` | gauge | `version` | Admin build information; always `1`. |
| `fleet_admin_http_requests_total` | counter | `method`, `route`, `status` | Completed admin HTTP requests. |
| `fleet_admin_http_request_duration_seconds` | histogram | `method`, `route` | Admin HTTP latency. |
| `fleet_admin_http_requests_in_flight` | gauge | - | Admin requests currently being served. |
| `fleet_admin_websocket_connections` | gauge | - | Open browser event WebSocket connections. |
| `fleet_admin_machines_online` | gauge | - | Machines with a live gateway connection. |
| `fleet_admin_event_bus_subscribers` | gauge | - | Active platform event bus subscribers. |
| `fleet_admin_event_bus_dropped_total` | counter | - | Events dropped for lagging subscribers. |
| `fleet_admin_durable_events_total` | counter | `outcome` (`applied`, `duplicate`, `failed`) | Durable agent events processed by outcome. |
| `fleet_daemon_build_info` | gauge | `version`, `protocol` | Daemon build information; always `1`. |
| `fleet_daemon_uptime_seconds` | gauge | - | Seconds since the daemon services started. |
| `fleet_daemon_active_sessions` | gauge | - | Sessions currently in an active state. |
| `fleet_daemon_event_queue_depth` | gauge | `lane` (`state`, `delta`, `overflow`) | Events waiting for dispatch per pipeline lane. |
| `fleet_daemon_dropped_ephemeral` | gauge | - | Ephemeral deltas dropped because the delta lane stayed full. |
| `fleet_daemon_rejected_events` | gauge | - | Durable events the store permanently rejected. |
| `fleet_daemon_storage_degraded` | gauge | - | `1` while the durable outbox is failing to persist. |
| `fleet_daemon_connection_up` | gauge | - | `1` while the delivery loop sees a connected admin transport. |
| `fleet_daemon_reconnects_total` | counter | - | Reconnects after the first successful connection. |

Histogram buckets for admin request latency are `0.005, 0.01, 0.025, 0.05,
0.1, 0.25, 0.5, 1, 2.5, 5, 10` seconds.

### Example queries and alerts

```promql
# Machines that are offline while the admin is up.
fleet_admin_machines_online == 0

# Daemon event backlog growing across the pipeline.
sum(fleet_daemon_event_queue_depth) > 1000

# The durable outbox cannot persist.
fleet_daemon_storage_degraded == 1

# Admin HTTP 5xx rate.
sum(rate(fleet_admin_http_requests_total{status=~"5.."}[5m])) > 0

# Machines online but no browser is subscribed to events.
fleet_admin_machines_online > 0
  and on() fleet_admin_websocket_connections == 0
```

```yaml
groups:
  - name: fleet
    rules:
      - alert: FleetNoMachinesOnline
        expr: fleet_admin_machines_online == 0
        for: 5m
        labels:
          severity: critical
        annotations:
          summary: No machine has a live connection to fleet-admin.
      - alert: FleetEventQueueGrowing
        expr: sum(fleet_daemon_event_queue_depth) > 1000
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: The daemon event pipeline is not draining.
      - alert: FleetStorageDegraded
        expr: fleet_daemon_storage_degraded == 1
        for: 2m
        labels:
          severity: critical
        annotations:
          summary: The daemon cannot persist its durable event outbox.
      - alert: FleetAdmin5xx
        expr: sum(rate(fleet_admin_http_requests_total{status=~"5.."}[5m])) > 0
        for: 10m
        labels:
          severity: warning
        annotations:
          summary: fleet-admin is returning server errors.
      - alert: FleetNoEventSubscribers
        expr: fleet_admin_machines_online > 0 and on() fleet_admin_websocket_connections == 0
        for: 15m
        labels:
          severity: warning
        annotations:
          summary: Machines are online but no browser receives events.
```

## Verify

```bash
fleet status
fleet doctor
fleet admin health
fleet admin config validate
fleet daemon config validate
```

A healthy host exits `0` from `fleet status`, has no `FAIL` from `fleet doctor`,
returns a version from `fleet admin health`, and prints no validation errors.

## Troubleshoot

| Symptom | Likely cause | Fix |
| --- | --- | --- |
| Status exits `2` | A process is running but health or config is degraded | Read the status output and the role log; run `fleet doctor`. |
| Status exits `1` | A role is stopped or cannot start | Start it with the intended `--mode`, then check logs. |
| Two processes fight over one role | A supervisor and a native service are both active | Stop one manager, then restart with explicit `--mode`. |
| Port already in use | Another process holds `8787` (admin) or `18080` (daemon) | Stop the conflict, or change the bind or daemon port. |
| Permission denied on key or token | File mode is too open or the owner is wrong | Use `0600` for key and token files and `0700` for data directories. |
| `storage_meta` role error | The admin and daemon point at the same database or swapped paths | Restore the correct database path for each role. |
| Logs are empty | The wrong log source or mode was selected | Retry with `--mode service` or `--mode supervisor`. |
| Service unit installed but inactive | The unit failed to start | Run `fleet <role> logs`, then check `systemctl status` on Linux. |
| Upgrade has no effect | The service still points at the old binary | Reinstall the service or pass `--bin` to the new binary. |

For exact flags, see [CLI](/reference/cli/) and
[Configuration](/reference/configuration/). For error codes, see
[Errors](/reference/errors/).
