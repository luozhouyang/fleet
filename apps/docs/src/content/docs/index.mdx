**agent-fleet** is a self-hosted control plane for coding agents that run on
machines you own. It gives you one browser UI for starting agent sessions,
browsing code, reviewing Git changes, and approving tool permissions — while
the agents, repositories, and credentials stay on your hardware.

The project is built for developers who want the convenience of a hosted coding
agent without handing their filesystem or shell to a third party. A small daemon
runs on each machine, owns the local workspace and agent processes, and connects
out to the admin. The admin routes requests; it never reads your files directly.

## How it fits together

<pre class="mermaid">{`
flowchart LR
  B["Browser SPA"] -->|"HTTPS + bearer token"| A["agent-admin"]
  C["af CLI"] -->|"HTTPS + bearer token"| A
  A -->|"reverse WSS /ws/machine"| D["agent-daemon"]
  D --> W["Workspaces"]
  D --> P["Agent providers"]
  D --> G["Git repositories"]
  D --> F["Local filesystem"]
`}</pre>

| Component | Responsibility |
| --- | --- |
| `agent-admin` | Serves the web UI and REST API, authenticates users, authorizes requests, keeps durable metadata, and routes RPCs to connected machines. |
| `agent-daemon` | Runs on the machine that owns the code. It registers workspaces, reads files, runs Git, spawns agents, and streams events back to the admin. |
| Web UI | Machine dashboard, workspace explorer, Monaco viewer/diff, Git panel, and streaming agent sessions. |
| `af` CLI | A thin REST client for machines, workspaces, sessions, users, organizations, audit entries, and network setup. |

A daemon opens a single outbound WebSocket to the admin and keeps it open. A
machine enrolls once with a single-use pairing code and receives its own
per-machine token; every later connection presents that token, and a per-machine
Ed25519 key proves which machine is connecting. The key is pinned during
pairing, and later key changes require a proof signed by the previously pinned
key.

## What you can do today

| Capability | What you get |
| --- | --- |
| Agent sessions | Create multiple sessions per workspace, stream messages and tool calls, approve or reject permissions, interrupt, resume, and close/archive. Close keeps history but hides the session from the default list; delete removes the session and its history permanently. |
| Session recovery | Turns, messages and tool calls persist in the daemon's SQLite database, which owns the transcript. Sessions restored after a restart are read-only `interrupted` records with their history intact; running turns and tools are closed and pending permissions become cancelled. Terminal history remains readable with no restore cap. The admin proxies history and reports it as unavailable when the machine is offline. |
| Providers | `mock` for deterministic tests, Claude Code CLI, Codex app-server, OpenCode serve, and a generic PTY adapter. Providers report unavailable when their binary is missing. |
| Workspace | Register repositories or directories, browse a lazy directory tree, search, read files with ETag caching, and react to file changes. Deleting a workspace returns 409 while active sessions remain. |
| Git | Status, branches, log, summaries, unified diffs, untracked files, stage/unstage, commit, and checkout. Writes sit behind an independent token and audit log. |
| Access control | Bearer tokens, `admin` / `member` / `viewer` roles, organization-scoped resources, machine key pinning, key rotation, permanent machine revocation/unrevocation, and an auth gate in the SPA. |
| Operations | Single web-serving admin process, SQLite storage, `af` management CLI, Docker-based verification, and black-box E2E scripts. |

## Current status

The supported release is the **single-machine version**: one `agent-admin`
manages one `agent-daemon`, and that daemon can host multiple workspaces and
sessions. Multi-machine fleets, remote access across NAT, multi-instance high
availability, and multi-tenant operations are on the roadmap, not part of the
current support commitment.

The full breakdown — what is complete, what remains for the single-machine
milestone, and the path from `v0.1` to `v1.0` — lives on the
[development status page](/progress/).

## Quick start

Prerequisites: Rust 1.85+, Node.js 22, pnpm 10, and Git.

```bash
pnpm install

# Terminal 1: build the SPA and start the admin on http://127.0.0.1:8787
pnpm dev

# Terminal 2: pair the machine once, then start the daemon
pnpm run af -- --url http://127.0.0.1:8787 --token dev-token setup \
  --org org_default \
  --server ws://127.0.0.1:8787/ws/machine \
  --daemon-config ~/.agent-fleet/config.toml \
  --name dev-machine
pnpm dev:daemon
```

`af setup` creates a single-use pairing code, completes the Ed25519
challenge-response handshake and stores the per-machine token in
`~/.agent-fleet/machine.key.token` (mode 0600). There is no shared machine
token to configure.

Open `http://127.0.0.1:8787`, select the machine, register a workspace, and
create a session. The `mock` provider works without external credentials; choose
`claude`, `codex`, or `opencode` when the corresponding CLI is installed.

`pnpm dev` injects the development admin token into the SPA. Production builds
embed no default token; if no token is stored or a request returns 401, the SPA
shows an auth gate.

## Project layout

```text
apps/fleet-admin      control plane: REST, WebSocket, SPA hosting
apps/fleet-daemon     machine daemon: agents, workspace, Git
apps/fleet-cli        af management CLI
apps/web              React web UI
apps/docs             this documentation site
crates/*              protocol, auth, storage, workspace, git, runtime, gateway
crates/admin-storage  admin database, repositories and migrations
crates/daemon-storage daemon database, transcript repositories and migrations
scripts/test          API, Git, browser, and multi-machine E2E scripts
```
