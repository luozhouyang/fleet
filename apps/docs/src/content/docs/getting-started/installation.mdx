Fleet ships as three binaries — `fleet-admin`, `fleet-daemon`, and the `fleet`
CLI — plus the web UI that the admin serves. There are two supported install
paths:

1. **Release installer (recommended).** One command downloads a verified archive
   for your platform, installs the binaries and web assets, configures both
   roles, and installs system services that start at boot.
2. **Source build.** Build the workspace and web UI yourself, stage the same
   directory layout as a release archive, and run `fleet install --from-dir`.

## One deployment profile

Fleet has exactly one deployment profile: **server**. The invoking user owns
everything that holds data, and the host's service manager starts the processes
at boot:

| Item | Location |
| --- | --- |
| Configuration, keys, databases, logs | `~/.fleet/<role>/` |
| Installed binaries | `~/.local/bin/` (override with `--prefix`) |
| Web assets | `<prefix>/share/fleet/web` |
| macOS service definitions | `/Library/LaunchDaemons/dev.fleet.<role>.plist` |
| Linux service definitions | `/etc/systemd/system/fleet-<role>.service` |
| Windows service definitions | Task Scheduler tasks `fleet-admin` and `fleet-daemon` |

The services run **as the invoking user**, never as root or LocalSystem. That
keeps the daemon inside the account that owns the repositories, coding agents,
and credentials. Configuration and state are never written as root, and Fleet
never executes `sudo fleet`.

Elevation is requested once, only for fixed commands that write service
definitions (`/Library/LaunchDaemons`, `/etc/systemd/system`, or Task
Scheduler). `fleet install --yes` uses passwordless sudo on Unix and still shows
the Windows UAC prompt; without passwordless sudo the installer prints the exact
elevated commands and exits non-zero rather than prompting repeatedly.

## Install with the release installer

<Steps>

1. **Review the script.** Piping a remote script into a shell executes it with
   your privileges. Download it first if you want to read it:

   ```bash
   curl -fsSLO https://luozhouyang.github.io/fleet/install.sh
   less install.sh
   sh install.sh
   ```

   Or run it directly:

   ```bash
   curl -fsSL https://luozhouyang.github.io/fleet/install.sh | sh
   ```

2. **Choose a prefix.** The default is `~/.local` and the installer refuses to
   run as root:

   ```bash
   curl -fsSL https://luozhouyang.github.io/fleet/install.sh | \
     sh -s -- --prefix "$HOME/.local"
   ```

3. **Pin a version** when you do not want the latest release:

   ```bash
   curl -fsSL https://luozhouyang.github.io/fleet/install.sh | \
     sh -s -- --version v0.2.2
   ```

4. **Add the binaries to your `PATH`** if the prefix is not already on it:

   ```bash
   export PATH="$HOME/.local/bin:$PATH"
   ```

   Add that line to your shell profile to keep it.

</Steps>

The installer detects `linux` / `darwin` and `x86_64` / `arm64`, downloads
`fleet-<os>-<arch>.tar.gz` from the
[GitHub releases](https://github.com/luozhouyang/fleet/releases), verifies it
against the release's `SHA256SUMS`, and installs:

| Path | Contents |
| --- | --- |
| `<prefix>/bin/fleet` | Management CLI |
| `<prefix>/bin/fleet-admin` | Control plane |
| `<prefix>/bin/fleet-daemon` | Machine daemon |
| `<prefix>/share/fleet/web` | Built web UI served by `fleet-admin` |
| `<prefix>/share/fleet/install.json` | Install manifest (version, port, files, services) |
| `~/Applications/Fleet.app` (macOS) | App bundle that names launchd jobs in Login Items & Extensions |

Linux archives are statically linked against musl. They do not depend on the
host glibc version, so the same archive works on current and older
distributions.

<Aside type="note" title="The installer needs a published release">
  Releases are produced by the `Release` GitHub Actions workflow when a `v*` tag
  is pushed. If no release exists for your platform yet, use the
  [source build](#build-and-install-from-source).
</Aside>

### Platform notes

<Tabs>
<TabItem label="Linux">

The installer writes systemd units to `/etc/systemd/system` and asks for sudo
once. The units use `User=<you>`, `Environment=HOME=<your home>`, and
`ProtectHome=false`; there are no dedicated service users and no environment
files. The admin and daemon read and write only `~/.fleet`.

```bash
curl -fsSL https://luozhouyang.github.io/fleet/install.sh | sh
```

If sudo is unavailable, the installer stages the unit files, prints the exact
`sudo install …` and `systemctl enable --now` commands, and exits non-zero.
Run those commands, then `fleet status`.

</TabItem>
<TabItem label="macOS">

The same installer detects `darwin` and installs into `~/.local` by default.
It also copies `Fleet.app` to `~/Applications` and registers it with
LaunchServices. The bundle is what makes macOS show **Fleet** instead of the
Developer ID certificate name in **System Settings → General → Login Items &
Extensions**; a bare signed binary has no display name, so macOS falls back to
the signer. Use `--no-app` to skip the bundle, or `--app-dir DIR` to install it
elsewhere.

Fleet manages macOS processes with launchd. It writes LaunchDaemons to
`/Library/LaunchDaemons` that run at boot, before login, as your account:

```bash
curl -fsSL https://luozhouyang.github.io/fleet/install.sh | sh
```

The daemon survives logout and does not depend on a GUI session. Two macOS
constraints still apply:

- **TCC:** protected folders (Desktop, Documents, Downloads, removable volumes)
  are granted per executable. Grant `fleet-daemon` access in **System Settings →
  Privacy & Security** after installing; a boot-time daemon cannot show a TCC
  prompt itself.
- **FileVault:** before the first unlock after a reboot, the data volume is not
  mounted, so Fleet cannot start until someone unlocks the disk. This is a
  platform limit, not a Fleet service failure.

Logs are written to `~/.fleet/<role>/logs/<role>.log` and rotate at 10 MiB with
one backup. Launchd's own `.out.log`/`.err.log` files capture only early panics.
State lives under `~/.fleet`.

Tunnel clients are available from Homebrew:

```bash
brew install cloudflared
brew install --cask tailscale
```

Tailscale still requires a GUI approval for the VPN/network extension. See
[Remote access](/guides/remote-access/).

<Aside type="caution" title="macOS signing depends on the release secrets">
  When the repository has Apple signing secrets configured, the macOS archives,
  including `Fleet.app`, are signed with a Developer ID and notarized; the app's
  ticket is stapled for offline Gatekeeper checks. Unsigned builds may be
  blocked by Gatekeeper; allow them in **System Settings → Privacy & Security**,
  or build from source if your policy requires a locally built artifact.
</Aside>

</TabItem>
<TabItem label="WSL2">

Use the Linux installer inside the distribution. Inside WSL2, use systemd when
it is enabled; otherwise install files only and run the processes in the
foreground or through the fallback supervisor.

- Keep repositories in the WSL filesystem (for example, under `~/code`), not on
  `/mnt/c`; cross-filesystem access is slow and can break file watches.
- With systemd enabled, the normal installer works. Without systemd, run
  `sh install.sh --no-service`, then `fleet admin setup --no-install-service`
  and `fleet daemon setup --no-install-service` to use the supervisor.
- Open `http://127.0.0.1:8787` in a Windows browser. WSL2 forwards loopback, so
  the admin is reachable without publishing the port.

</TabItem>
<TabItem label="Windows">

Run the PowerShell installer from a normal, non-elevated prompt:

```powershell
irm https://luozhouyang.github.io/fleet/install.ps1 | iex
```

The bootstrap downloads and verifies the zip, then runs `fleet.exe install`.
Fleet installs into `%LOCALAPPDATA%\Fleet` by default and asks for elevation
through UAC once. The elevated process registers two Task Scheduler tasks:

- `fleet-admin` and `fleet-daemon` start at boot with a stored credential and
  run as your account, not `LocalSystem`.
- `LogonType=Password` means a password change or expiry breaks the stored
  credential; rerun the installer to refresh it.
- A blank-password, Windows Hello-only, or some federated account may not
  support stored-credential startup tasks.
- The tasks use `LeastPrivilege` and have no execution time limit. Task
  Scheduler captures no stdout, so both binaries log to
  `%USERPROFILE%\.fleet\<role>\logs\<role>.log` with the same 10 MiB rotation.

```powershell
# Add the CLI to PATH for this session, or set it permanently in
# System Properties -> Environment Variables.
$env:PATH = "$env:LOCALAPPDATA\Fleet\bin;$env:PATH"

# Check the installed tasks
schtasks /Query /TN fleet-admin /V
schtasks /Query /TN fleet-daemon /V

# Open the admin
Start-Process http://127.0.0.1:8787
```

Configuration, keys, databases, and logs all live under
`%USERPROFILE%\.fleet`. There is no `%ProgramFiles%` or `%ProgramData%`
installation for the server profile.

If `fleet uninstall` cannot delete a task, run it once from an elevated
PowerShell; task deletion follows the usual Task Scheduler ACLs.

<Aside type="note" title="Windows watchdog status">
  Linux and macOS installs include the root-owned watchdog. The Windows
  SYSTEM-task watchdog is not registered by this build yet; Windows relies on
  the tasks' `RestartOnFailure` policy plus startup recovery. `fleet doctor`
  reports the watchdog only on platforms where it is installed.
</Aside>

</TabItem>
</Tabs>

### Installer options

| Option | Default | Effect |
| --- | --- | --- |
| `--version VERSION` | `latest` | Release to install, for example `v0.2.2` |
| `--prefix DIR` | `~/.local` (Windows: `%LOCALAPPDATA%\Fleet`) | Installation prefix for binaries and web assets |
| `--port PORT` | `8787` | Admin loopback port; the installer refuses a port that is already bound |
| `--yes` | off | Never prompt for sudo; requires passwordless sudo |
| `--no-service` | off | Copy files only; do not install the service definitions |
| `--no-app` | off | macOS: skip the `Fleet.app` wrapper |
| `--app-dir DIR` | `~/Applications` | macOS: app bundle location |
| `--force` | off | Replace existing binaries |
| `--dry-run` | off | Print the resolved plan and exit |

Environment variables `FLEET_VERSION`, `FLEET_PREFIX`, and `FLEET_BASE_URL`
override the version, prefix, and download base for mirrors or local tests.

### Repair

`fleet install --repair` re-renders and reloads the service definitions and the
watchdog from the installed configuration without replacing binaries. Use it
after changing `PATH`, after a macOS TCC change, or when `fleet doctor` reports
a missing service or watchdog.

```bash
fleet install --repair
```

## Requirements

The release installer needs:

| Requirement | Why |
| --- | --- |
| `curl` | Downloads the release archive and checksums |
| `tar` | Extracts the archive |
| `sha256sum` or `shasum` | Verifies the archive when `SHA256SUMS` is available |
| `sudo` (Linux, macOS) | Installs the fixed service definitions once |
| systemd (Linux) or launchd (macOS) | Hosts the processes at boot |

The watchdog needs `curl` at runtime on Unix and PowerShell 5.1 on Windows. It
runs as root/SYSTEM so it can restart the system services, but it executes only
fixed commands: no eval, no sourcing, and no Fleet binary.

A source build additionally needs:

| Requirement | Version |
| --- | --- |
| Rust | 1.89 or newer |
| Node.js | 22 |
| pnpm | 12.23 |
| Git | Recent release |

## Build and install from source

<Steps>

1. **Install JavaScript dependencies.** From the repository root:

   ```bash
   pnpm install
   ```

2. **Build the release binaries.** The scripts call `cargo` from your `PATH`:

   ```bash
   pnpm build:release
   ```

   This builds `fleet-admin`, `fleet-daemon`, and `fleet` into
   `target/release/`. To build only the CLI, run `pnpm build:cli`.

3. **Build the web UI.**

   ```bash
   pnpm build:web
   ```

   The output lands in `apps/web/dist`, which the admin serves.

4. **Stage a release-shaped directory and install it.**

   ```bash
   rm -rf target/fleet-dist
   mkdir -p target/fleet-dist/bin
   cp target/release/fleet target/release/fleet-admin target/release/fleet-daemon \
     target/fleet-dist/bin/
   cp -R apps/web/dist target/fleet-dist/web

   ./target/release/fleet install --from-dir target/fleet-dist
   ```

   `fleet install` writes user files without elevation, then asks for sudo once
   (UAC on Windows) to install the service definitions. Pass `--no-service` to
   stop after the file copy, or `--dry-run` to print the plan.

</Steps>

On macOS, build and install the app bundle so Login Items shows **Fleet**:

```bash
scripts/release/package-macos.sh \
  --bin-dir target/release --web-dir apps/web/dist --output-dir dist
cp -R dist/Fleet.app ~/Applications/Fleet.app
```

## Paths

The server profile has one set of paths, regardless of platform:

| Item | Location |
| --- | --- |
| Admin config | `~/.fleet/admin/config.toml` |
| Admin database | `~/.fleet/admin/fleet-admin.db` |
| Daemon config | `~/.fleet/daemon/config.toml` |
| Daemon database | `~/.fleet/daemon/fleet-daemon.db` |
| Machine key | Under the daemon state directory |
| Machine token | Next to the machine key |
| Logs | `~/.fleet/<role>/logs/<role>.log` |
| Web assets | `<prefix>/share/fleet/web` |
| Install manifest | `<prefix>/share/fleet/install.json` |

`~/.fleet` must be owned by you and mode `0700`; installer files have their own
modes (`0600` for configuration and tokens, `0644` for service definitions,
`0755` for binaries and the watchdog script). The installer refuses to proceed
over a root-owned `~/.fleet` and prints the `chown` command to fix it.

<Aside type="caution" title="No migration from pre-server-profile installs">
  This release has no backward compatibility. Remove old root-owned service
  units, `/etc/fleet`, `/var/lib/fleet`, `%ProgramData%\fleet`, and a root-owned
  `~/.fleet` before installing. The installer does not import their databases,
  keys, or tokens.
</Aside>

## Verify the installation

Run the read-only checks first. If you installed into `~/.local`, make sure
`~/.local/bin` is on `PATH`:

```bash
fleet status
fleet doctor
```

`fleet status` reports both roles and exits `0` when both are healthy, `1` when
a role is stopped, and `2` when a role is degraded or unhealthy. `fleet doctor`
runs read-only configuration, service, and watchdog checks and exits `1` if any
check fails.

Probe readiness directly:

```bash
curl -fsS http://127.0.0.1:8787/api/v1/ready
```

`/api/v1/ready` returns `200` only after the database is reachable, migrations
are current, and the web index exists. During startup it returns `503` with the
failing checks. `/api/v1/health` remains the liveness endpoint.

Then open `http://127.0.0.1:8787` in a browser. Production builds embed no
default token, so the UI shows an auth gate until you enter one. The admin token
is stored in `~/.fleet/admin/config.toml` and can be read with
`fleet admin config show --reveal`. User tokens minted in the UI use the `flu_`
prefix.

If the admin is healthy but the daemon is not paired, follow
[Enroll a machine](/guides/enroll-a-machine/) or continue with the
[quick start](/getting-started/quick-start/).

## Upgrade

`fleet upgrade --yes` replaces the binaries and web assets from a verified
release archive, restarts the native services, and checks `/api/v1/ready`
before declaring success. If a service does not become ready, the previous
binaries and web assets are restored and the services are restarted with them.
The database schema is not promised to be backward compatible across major
versions; take a backup before upgrading production data.

```bash
fleet upgrade --yes
```

A non-interactive `--yes` upgrade restarts system services with `sudo -n`, so
it requires passwordless sudo on Linux and macOS; run it from a terminal
without `--yes` to get one prompt instead. If a restart or readiness check
fails, the upgrade restores the previous binaries and web assets and restarts
them.

To reinstall through the release installer instead, rerun it with `--force`:

```bash
curl -fsSL https://luozhouyang.github.io/fleet/install.sh | \
  sh -s -- --force
```

Rerunning the installer refreshes the service definitions, the watchdog, and
the macOS app bundle. After upgrading from an older layout, run
`fleet install --repair` once so launchd picks up file logging and the watchdog.

## Uninstall

```bash
fleet uninstall --yes
```

This removes both native services, the watchdog, the installed binaries, web
assets, and the macOS app bundle. Configuration and data under `~/.fleet` are
kept unless you pass `--purge`:

```bash
fleet uninstall --yes --purge
```

On macOS and Linux the removal uses the same fixed sudo commands as the
installer. On Windows it removes the Task Scheduler tasks.
