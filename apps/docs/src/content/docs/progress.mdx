The supported scope for the current phase is the **single-machine release**:
one `fleet-admin` instance manages one `fleet-daemon`, and the daemon host can
run multiple workspaces and agent sessions. Multi-machine fleets, remote
connectivity, high availability, and multi-tenant operations belong to later
roadmap phases.

<Aside type="caution" title="Multi-machine code is not a product commitment yet">
  `admin-machine`, the organization/role model, and the multi-machine stress
  suite already exist as groundwork and regression coverage for the later
  multi-machine release. This phase officially supports only "one admin + one
  daemon + multiple workspaces/sessions on that daemon". The features required
  to operate a fleet — pairing codes, multi-endpoint failover, resumable event
  streams, site relays, and HA leases — are not productized yet.
</Aside>

## Status at a glance

| Item | Current state |
| --- | --- |
| Current milestone | `v0.1.0` single-machine MVP — feature-complete, now in hardening |
| Supported topology | 1 `fleet-admin` + 1 `fleet-daemon` |
| Persistence | SQLite only; no Redis or NATS |
| Default provider | `mock` — deterministic, used by E2E, no credentials |
| Real providers | Claude Code CLI, Codex app-server, OpenCode serve, generic PTY |
| Web UI | SPA served by `fleet-admin`; REST + WebSocket |
| Management entry point | Browser SPA; `fleet` CLI as a REST client |
| Deployment | Local host or LAN; TLS must terminate in front of the admin in production |

flowchart LR
  U["Browser / fleet"] -->|"HTTPS + WSS"| A["fleet-admin<br/>one instance"]
  A -->|"reverse WSS<br/>/ws/machine"| D["fleet-daemon<br/>one process"]

Single-machine does not mean single-workspace. One daemon can register multiple
workspaces, and each workspace can host multiple sessions. They share the same
host filesystem, Git repositories, and agent processes.

## What is already complete

### Engineering foundation and protocol

| Area | Delivered | Notes |
| --- | --- | --- |
| Monorepo | Cargo workspace + pnpm workspace | `apps/*`, `crates/*`, `packages/*`; dependency direction is documented |
| Build and checks | Root `package.json` scripts | `build:rust`, `build:web`, `fmt`, `lint`, `test`, and more |
| CI | GitHub Actions | Rust fmt/clippy/test, web typecheck/lint/build, browser E2E, stress suite |
| Protocol | DTOs, connection envelope, RPC contract | `crates/core-protocol`, with serde and compatibility tests |
| Data model | Session / Turn / Message / ToolCall / Permission / Event | Unified event model; provider output maps into one event stream |

### Daemon, runtime, and providers

| Area | Delivered | Notes |
| --- | --- | --- |
| Daemon foundation | Config loading, SQLite migrations, process manager, Ed25519 identity | Defaults < TOML < environment; `serve` and `rotate-key` commands |
| Local mode | Runs without `server_url` or token | Workspaces and agents work; no admin connection |
| Agent runtime | Unified session state machine, event sequencing, permission hub, authoritative persisted turns/messages/tool calls | Streaming messages, tool calls, interrupt, resume, close; daemon restart restores read-only `interrupted` sessions with `metadata.restored=true`; the admin proxies history instead of mirroring it |
| Claude Code | `stream-json` + partial messages | Streaming text, tools, interrupt, resume; no interactive permission prompts; reports `available: false` when the binary is missing |
| Codex | app-server JSON-RPC | Streaming, tools, approvals, interrupt, resume; reports `available: false` when the binary is missing |
| OpenCode | HTTP API + SSE | Streaming, tools, approvals, interrupt, resume, session persistence |
| Generic PTY | Raw terminal stream | Works with arbitrary CLIs; supports interrupt; reports `available: false` when the binary is missing |
| Provider tests | Fixtures + mock server | Protocol regression without real CLIs; real providers need host credentials |

### Workspace and Git

| Area | Delivered | Notes |
| --- | --- | --- |
| Workspace registration | Root canonicalization and allowlist | Optional restriction on directories that may be registered |
| Directory tree | Lazy loading, pagination, ignore rules | The full tree is never loaded at once |
| File reads | ETag, caching, size limits, binary detection | Large files are truncated and marked; read-only |
| Search | Workspace-scoped search | Results constrained by the path policy |
| File watching | Debounced watcher | Refreshes Git status and the UI after changes |
| Path security | `PathPolicy` | Rejects absolute paths, `..`, symlink escapes, and the filesystem root |
| Git reads | status, diff, summary, branches, log | Porcelain v2, unified diff, untracked diffs |
| Git writes | stage/unstage/commit/checkout | Independent write switch and token; path/branch validation; conflicts return 409 |
| Audit | Write-operation audit log | Queryable through `GET /api/v1/audit`; failures do not roll back an executed command |

### Connection, admin, and web UI

| Area | Delivered | Notes |
| --- | --- | --- |
| Reverse connection | Daemon-initiated outbound WSS `/ws/machine` | Machines never listen for inbound admin traffic |
| Machine authentication | Pairing code -> per-machine token + Ed25519 challenge-response | The key is pinned during pairing; rotation requires a proof signed by the old key |
| Connection reliability | Heartbeats, ACKs, exponential backoff, request timeouts, response correlation | Per-connection event sequence; durable agent events replay from a transactional outbox after reconnect |
| Durable event delivery | Transactional outbox + out-of-order-safe consumer cursor in `daemon-storage` | Projection rows and outbox entries commit together; the runtime dispatcher uses a lossless queue; the admin deduplicates by `event_id` and acknowledges each applied sequence with `events.ack`; gaps are retained and unacknowledged events replay until applied |
| Admin REST | machines / workspaces / git / sessions / permissions / users / orgs / audit | Organization-scoped filtering; `admin` / `member` / `viewer` roles; session close archives history while delete removes it permanently; workspace deletion returns 409 while active sessions remain |
| Machine revocation | Permanent revoke, disconnect and active-row removal | Revoked daemons stop reconnecting; `GET /machines/revoked` and `POST /machines/{id}/unrevoke` list and restore pairing |
| Browser events | Browser WebSocket `/api/v1/events` | EventBridge → session store → React; REST polling fallback; ping frames and a `platform.lagged` notice that triggers a refetch |
| SPA hosting | Admin serves the frontend build | Same process in development and production; Vite proxy also supported |
| Web auth | Production builds embed no default token | Dev builds inject `VITE_DEFAULT_API_TOKEN`; missing token or a 401 shows an auth gate |
| UI features | Machine dashboard, workspace tree, Monaco viewer/diff, Git panel, session stream, tool cards, permission approvals, reconnect, Git writes | Sessions grouped under workspaces, with inline creation; restored sessions are read-only and marked as recovered |
| Management CLI | `fleet` wraps the admin REST API | machines/workspaces/sessions/users/orgs/audit/permissions/config |
| Network wizard | Tailscale / Cloudflare detection, config generation, authorization, and `--execute` | Groundwork for remote access; not required by the single-machine release |

The multi-machine stress suite (3 daemons, 6 workspaces, roughly 100 concurrent
requests) remains as regression coverage for the connection and isolation
layers. It is not a supported multi-machine deployment model in this phase.

## What remains for the single-machine release

The following work is still required for the single-machine milestone. None of
it depends on multi-machine architecture.

| Priority | Item | Completion criteria |
| --- | --- | --- |
| P0 | Real-provider conformance | Run one real session each with Claude, Codex, and OpenCode; record versions and a capability matrix |
| P0 | Install and upgrade | Source install script and systemd units are delivered; still publish Linux/macOS binaries, add launchd/Homebrew packaging, and automate upgrade/rollback verification while preserving databases |
| P0 | Token lifecycle | User-token expiry and rotation UI; per-machine enrollment tokens; no shared default credentials on first start. Machine revocation/unrevocation is already implemented. |
| P1 | First-run experience | Onboarding wizard, empty states for machines/workspaces/sessions, actionable errors, accessibility |
| P1 | Complete OpenCode mapping | Structured diffs and image attachments; document Claude permission limitations and fallback behavior |
| P1 | Observability | Structured logs, health/metrics, diagnostic bundle, audit-log UI |
| P1 | Test hardening | UI component tests, E2E stability, performance budgets, migration regression |
| P2 | Advanced single-machine features | Remote file editing, Git push/merge/rebase, worktree management, agent sandboxing |
| P2 | Operations | Database backup/restore, version migration notes, troubleshooting guide |

### v0.1 — Single-machine MVP (current, complete)

**Goal:** close the full loop with one admin and one daemon.

- Machine registration, authentication, heartbeats, and reconnect;
- Workspace browsing, file reads, Git reads and writes;
- Agent session creation, streaming messages, tool calls, permission approvals,
  interrupt, close/archive, and permanent delete;
- Daemon restart recovery: persisted turns/messages, read-only `interrupted`
  restored sessions, and cancelled pending permissions;
- Permanent machine revocation and unrevocation;
- Browser SPA (with an auth gate) and `fleet` CLI;
- Unit, integration, API, browser E2E, and stress regression suites.

**Exit criteria:** from the browser, a user can open a machine, choose a
workspace, browse files and diffs, create a session, watch agent output stream,
approve a permission request, interrupt or close the session, and complete
stage/commit/checkout.

### v0.2 — Single-machine hardening (next)

**Goal:** make the single-machine release installable, upgradeable, and usable
by people who are not working on the codebase.

- Real-provider regression runs and a published capability matrix;
- Release binaries, service installation, upgrade, and rollback;
- User-token expiry/rotation, per-machine enrollment tokens, audit UI, and
  diagnostic bundle;
- First-run wizard, error recovery, and accessibility;
- Performance and stability budgets, plus UI component tests;
- Decide and begin the first advanced features: remote editing, Git
  push/merge, worktrees, and agent sandboxing.

**Exit criteria:** on a clean machine, a new user completes
workspace → session → Git commit within ten minutes of following the install
guide; upgrade and backup flows have automated verification.

### v0.3 — Multi-machine foundation

**Goal:** turn "multiple machines" from a code capability into an operable
product capability.

- Pairing codes + per-machine enrollment tokens, with expiry and enrollment
  audit (per-machine revocation and unrevocation are already implemented);
- Multiple admin endpoints, failover, and connection-health visibility;
- Complete resumable streams: today durable agent events use a cursor and
  at-least-once replay, while workspace/Git events and ephemeral deltas remain
  live-only; add a bounded cross-event queue and idempotent requests;
- HTTPS proxy support, custom CAs, and optional mTLS;
- Fleet UI: machine groups, filters, bulk workspace registration, and a
  cross-machine status view;
- Scale targets: connection and isolation tests at 10 / 50 / 100 daemons;
- Connection leases/fencing when more than one admin instance is deployed.

**Exit criteria:** 10 machines across 2 LANs reconnect independently and
converge to consistent state; no data leaks across machines or organizations;
a capacity and failure-drill report is published.

### v0.4 — Remote access

**Goal:** let daemons behind NAT, corporate firewalls, and isolated LANs reach
the admin.

- Tailscale Serve / WireGuard overlay access;
- Cloudflare Tunnel access and an Access-protected operating procedure;
- Generic HTTPS reverse-proxy configuration;
- Site relay for isolated LANs: local multiplexing, outbound connection, mTLS;
- DNS SRV / well-known discovery, QR bootstrap, and optional mDNS;
- Connection-quality monitoring and path selection; long-polling fallback when
  proxies block upgrades.

**Exit criteria:** reproducible deployment guides and E2E coverage for home NAT,
corporate proxy, and isolated-LAN scenarios; failover does not disrupt active
sessions.

### v0.5 — Teams and multi-tenancy

**Goal:** grow from a single-user, single-machine tool to a shared admin for a
team.

- Organization/user management UI, invitations, roles, and per-workspace ACLs;
- SSO/OIDC, token expiry and rotation, audit export, and retention policies;
- Quotas, rate limits, and payload-size limits;
- Multi-tenant isolation tests and operational audit.

**Exit criteria:** two organizations share one admin while resources, events,
audits, and quotas remain fully isolated; the role matrix is covered by
automated tests.

### v1.0 — Scale and collaboration

**Goal:** support parallel multi-agent development and long-running operations.

- Multi-agent/worktree orchestration with branch comparison and merge
  workflows;
- Session import/export, event replay, and agent templates;
- Provider SDK / plugin model, capability discovery, and version management;
- Multi-instance admin (Postgres/Redis/NATS), backup/restore, SLOs, and
  alerting;
- Agent sandboxing, remote editing, Git push/merge, and other advanced
  capabilities.

**Exit criteria:** production-grade deployment, upgrade, backup, capacity, and
failure drills; parallel agents cannot overwrite each other's working
directories.

### Explicitly out of scope for now

- Hosted multi-tenant SaaS;
- Mobile app;
- A full IDE in the browser;
- Arbitrary Git subcommands, force-push, or history rewriting;
- A daemon that listens on a public inbound port;
- An unaudited plugin marketplace.

If these are pursued, they will be evaluated separately after v0.4 and do not
consume the single-machine delivery scope.

## Verification entry points

```bash
pnpm test              # Rust + web typecheck/lint
pnpm e2e               # API smoke
pnpm e2e:ui            # Playwright browser E2E
pnpm e2e:git           # Git write E2E
pnpm e2e:multi         # multi-machine stress regression (not a supported topology)
pnpm docker:verify     # full verification in a clean Linux container
```

A milestone is complete only when its tests, E2E coverage, and documented exit
criteria all pass. Merged code alone is not a completion signal.
